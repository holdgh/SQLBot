## 二、Phase 1 范围与硬性约束（摘自 v1.2，必须遵守）

1. **改造标记**：工程惯例 `# ========= 【改造标记 XXX】↓ ... =========` / `↑ ... 结束`；**Phase 1 标记名定为 `METRIC-CENTER`**。
2. **旧代码不可删除**：必须注释掉并加改造说明与起止标记；新增代码必须加改造说明与起止标记。
3. **开关**：`METRIC_CENTER_ENABLED` 默认 **False**；关 = 与原版行为完全一致（filter 不执行、提示词无变化）；指标库为空 = 召回为空。
4. **不碰 SQL 生成**（`llm.py:generate_sql` 及其后链路不动）。
5. **规则 G1 薄插桩**：`llm.py` 只加调用与开关判断，业务实现全部落在 `backend/apps/metric/` 独立模块。
6. **alembic 只增不改**：新迁移 `072_metric_center`，只建 6 张表，可回滚；**2026-10-10 增补 `073_metric_source_ds`（只增列 `metric_definition.source_ds_id`，可回滚，已应用到本地库）**。
7. **字段别名走既有术语库**，不建 `column_business_term`。
8. **不提前抽象**：Phase 1 不建 `apps/semantic/` facade。

### 数据模型（6 张表）

- ① `metric_definition`：metric_name/description/business_domain/**oid/specific_ds/datasource_ids（照 `terminology_model.py:Terminology` 归属字段惯例）**/source_table/source_column/aggregation/filter_rule/time_field/**metric_type(atomic/derived/composite，默认atomic)**/**unit/normal_range(JSONB)/additivity(additive/semi/non，默认additive)**/status/**version**。
- ② `metric_alias`（metric_id/alias）
- ③ `metric_document`（metric_id/document_text/embedding/keyword_list 预留不物化，可整表重建）
- ④ `dimension`（dimension_name/aliases(JSONB)/default_column/description/oid）
- ⑤ `metric_dimension_relation`（metric_id/dimension_id/enabled）
- ⑥ `metric_dependency`（derived_metric_id/depends_on_metric_id/expression_hint）——**本期只建表，不实现 DAG 编译展开（规则 G5）**

**元数据与检索索引分离**：口径变更 → 重建 document，不动业务元数据。

### 检索与接入

- 检索：复用 BM25（`common/utils/keyword_retrieval.py:bm25_retrieve`）+ pgvector + 并入 `llm_filter_context`（`llm.py:llm_filter_context`）rerank；按 oid + 数据源过滤。
- 插桩点（薄插桩）：
  - ds 分支（`llm.py:run_task`，在 `filter_terminology_template` **之前**）新增 `self.filter_metric_template(_session, oid, ds_id)`；
  - 无 ds 分支（同在 `llm.py:run_task`，同样在 `filter_terminology_template` 之前）；
  - `init_messages` 的 terminologies 块**之前**注入 metrics 消息块（"相关业务指标"，含支持维度列表与 derived 定义）；
  - `llm.py:llm_filter_context` 把指标候选项并入 rerank。
- derived 指标 MVP：仅文档化展示（定义随指标块注入提示词），compiler 自动展开 = 后续能力。

### 验收标准

- 开关关 = 回归与基线无差异；
- 开关开 = 业务词问题提示词出现正确指标；
- 多数据源指标正确隔离；
- derived 指标录入后可被召回并在提示词中展示定义。

### 3.2 注入链路（llm.py + chat_model.py + template.yaml）

- `AiModelQuestion`（`chat_model.py:AiModelQuestion`）：`terminologies`、`data_training`、`custom_prompt` 字段。
- `sql_sys_question`（`chat_model.py:sql_sys_question`）：`if self.terminologies: templates['terminologies'] = _base_template['generate_terminologies_info'].format(...)`（terminologies 分支）。
- `init_messages`（`llm.py:init_messages`）：消息顺序 system → rules → schema → custom_prompt → **terminologies** → data_training → 历史轮次。metrics 块要插在 terminologies 块之前。
- `llm.py:filter_terminology_template`：start_log(FILTER_TERMS) → 按 assistant 类型分流调 `get_terminology_template` → end_log → 暂存 `self._terminology_candidates`。
- `llm.py:filter_training_template`、`llm.py:filter_custom_prompts` 同构。
- `llm.py:llm_filter_context`：
  - 读取 `self._terminology_candidates / _data_training_candidates / _custom_prompt_candidates`；
  - 总数 < `LLM_CONTEXT_FILTER_MIN_CANDIDATES` 跳过；
  - 拼 `[术语]/[SQL示例]/[自定义提示词]` 分组编号 sections + `index_map(category, local_i)`；
  - LLM 返回 `{"retain":[编号]}` → 按 category 回写 `chat_question.{terminologies,data_training,custom_prompt}`；
  - **接入指标时需改**：total 计算、sections 加 `[指标]` 分组、`index_map` 加 `('metric', i)`、`filtered/source_map` 加 `'metric'` 键、回写 `chat_question.metrics`、summary counts。

#### B1 判别法与依据（2026-10-15 修订，替代初版"表集=检索命中表"措辞）

**为什么需要判别法**：B1 本质是验证生成 SQL 提示词中 schema 信息的**来源**——`choose_table_schema`（llm.py）写入 `chat_question.db_schema`，再经 `sql_sys_question` 注入 system/user 两处消息（`chat_model.py:sql_sys_question` 的 system 与 user 两处注入），这是 schema 进提示词的唯一链路。ds=1 仅 2 张勾选表且均建有 TABLE 文档，**文档检索与 DDL embedding 两条路径恰好选出同集同序的 2 张表**（5.3 冒烟实测：sim 序与 cosine 序同为 表1>表2），db_schema 逐字相同，肉眼无法判别来源——需人为制造两路径可分歧的场景（用户实测"实施前后 chat_log 无差异"即此原因，非验收失败）。

**判别原理（双粒度并集）**：`select_schema_doc_tables` 的结果 = TABLE 文档命中 ∪ COLUMN 文档宿主表（**"或"关系**，`schema_doc.py` 合并循环 table_rows+column_rows 去重）。因此：
- 仅改 COLUMN 行 ds_id：该表 TABLE 文档仍在 ds=1 → TABLE 查询直接命中，**无效**；
- 仅改 TABLE 行 ds_id：该表 COLUMN 行仍在 ds=1 → COLUMN 查询按宿主表（`split_part(object_key,'.',1)`）把它合并拉回，**同样无效**（初版"改一条 TABLE 行"建议错在此，2026-10-15 纠正）；
- **让表 X 从 ds=1 检索消失的充要条件：X 的 TABLE+COLUMN 文档全部改走**。

**操作步骤**：
1. `SCHEMA_DOC_ENABLED=true` 重启，问「游客来源地是哪里」，记录 db_schema 表集（应为 2 张）；
2. 整表文档改走（以表名为前缀，1 条 TABLE + N 条 COLUMN 一并）：
   ```sql
   UPDATE schema_document SET ds_id=2
   WHERE ds_id=1 AND (object_key='省内外游客数量' OR object_key LIKE '省内外游客数量.%');
   ```
3. 开关**开**再问：db_schema 应只剩另一张表（境外来游客数量）；`SCHEMA_DOC_ENABLED=false` 重启再问：仍为 2 张表（原路径不读 schema_document）——两侧差异即证明来源切换；
4. **恢复**：按 object_key 同条件 UPDATE 回 `ds_id=1`；**勿重跑 `apply-schema-docs`**——upsert 键含 `(ds_id, object_type, object_key)`，行停在 ds=2 时重跑 `--ds 1` 会新插一行并在 ds=2 留孤儿行。

**依据（代码链路）**：
- 原路径（开关关）：`get_table_schema` 默认 `embedding=True` → `calc_table_embedding` 用预存 `core_table.embedding` 与问题余弦排序取 top10（`datasource.py:calc_table_embedding` → `table_embedding.py:calc_table_embedding` 批量计算实现），**不读 schema_document**；
- 新路径（开关开）：`select_schema_doc_tables` 按 `ds_id` 过滤双粒度文档（`schema_doc.py`）→ `get_table_schema(embedding=False, table_list=...)` 跳过排序，表名在 `datasource.py:get_table_schema` 表名过滤处收敛；
- **字段信息不来自语义文档**：选中表的全部 `checked=True` 字段（admin 不裁剪，普通用户经列权限过滤）由 `core_table`/`core_field` 带出拼进 DDL（`datasource.py` 的 DDL 字段拼接实现）——语义文档只贡献"选哪些表"，故 B5 表结构变更无需同步改文档即可在 db_schema 反映字段变化。

> 目的分析与设计依据：`selfdoc/v201/detail/phase3可信校验层方案分析.md`（用户已认可）；权威规格：`v201改造方案_v1.2.md` 第四节 Phase 3 章节 + 全局规则 G1~G5（第三节）。全部改动带 `【改造标记 TRUST-VALIDATE】`。

### 6.1 实施口径与边界

- **3-A 口径校验**（`[TRUST-VALIDATE][METRIC-RULE] {json}` 告警日志，执行前静态）：
  ① **列存在性硬底线**（讨论结论 3.4-5）：sqlglot 解析 SQL，引用列须存在于对应勾选表 `core_field` 中；排除 CTE 引用、子查询/派生表别名、SELECT 计算别名防误报；未限定列名比对全部命中表字段并集。
  ② **指标规则**（新表 `metric_rule`，三类）：`required_filter` 字段须出现在 WHERE/HAVING、`forbidden_field` 禁止出现在 SQL、`forced_agg` 指标字段聚合方式必须相符（未聚合跳过防误伤）；按指标召回命中 + SQL 触及其 `source_table`/`source_column` 弱绑定才加载该指标规则（无命中零成本短路）。
- **3-B Result Validator**（`[TRUST-VALIDATE][RESULT] {json}` 告警日志，执行后动态；开关 `RESULT_VALIDATOR_ENABLED`）：L1 通用 = 空结果 / 行数超限（`RESULT_VALIDATOR_MAX_ROWS`=5000）/ 全 NULL 列 / 数值量级（`RESULT_VALIDATOR_MAX_VALUE`=1e12）；L2 指标级 = 命中指标 `normal_range{min,max}` 对结果同名列（`source_column` 或 `metric_name`）区间越界告警。
- **本期明确不做**（边界，分析文档同步标注）：
  - **零阻断**：不 raise、不改结果、不改前端（G4 先观测后阻断）；`METRIC_RULE_ENFORCE=False` 仅声明，消费者在 Phase 5（且 LLM 轨道始终告警，G2）；
  - **字段类型校验**（varchar 与数值直比）：误报率高，留待规则细化后补；
  - **主键重复检查**：`core_field` 无主键元数据，无法可靠判定，跳过；
  - **规则录入界面**：本期 SQL 手工插入（示例见 6.5），管理端入口与问题 5 治理页面化合并考虑。
- **G2 兜底**：两个校验器整体 try/except，任何内部异常只记日志、绝不阻断问数主流程。

**步骤 1：选定已录入指标**（记下 `id` 与 `source_column`，示例为库中实际形态）

FROM metric_definition WHERE status = 'enabled';

**违规条件（满足任一才出日志，共 5 类）**

| kind | 触发条件 | 最省事的构造方式 |
| --- | --- | --- |
| `result_empty` | SQL 返回 **0 行** | 问带不可能条件的问题，如「2030年元旦的游客量」 |
| `result_rows_exceeded` | 行数 > `RESULT_VALIDATOR_MAX_ROWS`（默认 5000） | 问不带任何过滤的大范围明细查询 |
| `result_all_null_column` | 某列全部为 NULL/空串 | 问含库中全空字段的查询 |
| `result_magnitude` | 某数值 > `RESULT_VALIDATOR_MAX_VALUE`（默认 1e12） | 正常数据难触发，可临时把配置改小（如 `1e3`）再问普通数值问题 |

### 6.6 日志解读（告警标志与发生场景）

> 供 C1~C3 走查与日后排障判读；全部 log-only——任何一条告警都不阻断问数（G2/G4）。

| 日志标志 | 级别 / 来源 | 发生场景 | 条数粒度 |
| --- | --- | --- | --- |
| `[TRUST-VALIDATE][METRIC-RULE] {json}`，`kind=metric_rule` | WARNING / `metric_validator` | 指标召回命中 + SQL 触及该指标 `source_table`/`source_column`（弱绑定）+ 违反其启用规则（`required_filter`/`forbidden_field`/`forced_agg`） | **每条被违反的规则一条** |
| `[TRUST-VALIDATE][METRIC-RULE] {json}`，`kind=column_missing` | WARNING / `metric_validator` | 同上前提下，SQL 引用的列不存在于对应勾选表 `core_field`（未限定列名不属于任何命中表勾选字段时 `table` 为空串） | **每个违规列一条** |
| `[TRUST-VALIDATE] parse SQL failed: ...` | ERROR / `metric_validator` | sqlglot 解析失败（挂接点在 check_sql 之后，正常不应出现，出现说明异常输入） | 每次失败一条 |
| `[TRUST-VALIDATE] load core fields failed: ...` | ERROR / `metric_validator` | `core_field` 查询异常：列存在性检查降级跳过，规则检查继续 | 每次故障一条 |
| `[TRUST-VALIDATE] metric rule check failed: ...` | ERROR / `metric_validator` | 校验器内部异常（G2 兜底：只记日志，绝不阻断问数） | 每次故障一条 |
| `[TRUST-VALIDATE][RESULT] {json}` | WARNING / `result_validator` | 仅 `RESULT_VALIDATOR_ENABLED=True` 时：L1 `result_empty`/`result_rows_exceeded`/`result_all_null_column`/`result_magnitude` 与 L2 `result_metric_range` | **每个违规一条**（全空/超限各一；列类检查每列至多一条） |

**判读要点**：

1. **无违规 = 完全静默**：3-A 不记「校验已执行」心跳日志（3-A 无独立开关，指标召回为空 = 零成本跳过；3-B 受开关控制），因此**日志条数 = 实际违规数**，不是每次问数一条；
2. 证明「每次都跑了、条数严格等于违规数」：再插一条必违反的规则后重问 → 应新增对应告警；
3. ERROR 级 = 校验器自身故障（与业务违规无关），出现即需排查，但当次问数不受影响；
4. JSON 内 `record_id` = `chat_record.id`，可与执行详情互证某笔问数的全部校验痕迹（如 `Select-String -Path .\logs\*.log -Pattern 'TRUST-VALIDATE'`）。

**Phase 3 验收闭环（2026-10-20）**：C1~C3 全部用户走查通过（记录见上方）；C1 测试规则（`forbidden_field`/游客数量）仍留库待清理，见第八节 #12。
