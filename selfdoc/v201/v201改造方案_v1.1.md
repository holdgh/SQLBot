# SQLBot 企业级问数改造方案 v1.1（分步实施版）

> 基于《v201改造方案.md》（v1.0）与《v201改造方案的检查意见_v1.md》的逐条评估收敛而来。
> 核心目标不变：将 SQLBot 从「RAG 增强型 Text2SQL」升级为「**Metric + DSL 驱动的企业级查询系统**」，
> **每个阶段完成后系统直接可运行**，后续阶段逐步叠加。

## 〇、v1.0 → v1.1 修订说明

| # | 检查意见 | 采纳 | v1.1 落点 |
| - | ---- | ---- | ---- |
| 1 | Phase 2 口径校验太早，拆"只记录/阻断"两级 | ✅ 部分采纳 | 拆为**告警级（Phase 3，问题侧弱绑定，log-only）**与**阻断级（Phase 5，Plan 强绑定）**；不整体后移——告警级对现有 LLM 轨道立即生效的价值保留 |
| 2 | Query Plan 缺 `datasource` 字段 | ⚠️ 修正落点 | **修 `metric_definition` 归属字段（oid/specific_ds/datasource_ids，照术语库惯例）**，必做；plan 不强制携带 datasource——现有链路 `select_datasource`（`llm.py:1486`）在 plan 生成前执行，数据源由链路外部承载 |
| 3 | Query Plan ≠ DSL，不是所有 Plan 都要编译 | ✅ 显式化 | v1.0 Phase 4 已有双轨制，v1.1 在 Phase 5 以"Plan 分流规则"独立小节重申 |
| 4 | Schema 语义治理应提前 | ✅ 采纳 | 原 Phase 6 提前为 **Phase 2（与指标中心并行）**——冷启动期指标覆盖率低，schema 检索是主干而非兜底 |
| 5 | 计算引擎分三类，定位 Post Query Calculation Engine | ✅ 精化 | Phase 6 明确三类分工边界（SQL 聚合/Post-Query 业务公式/统计分析后置） |
| 6 | 缺 Result Validator（结果验证层） | ✅ 采纳 | 新增 **Phase 3「可信校验层」**：L1 通用异常 + L2 指标级 unit/范围校验，全部默认 log-only |
| 7 | 补 `metric_dimension_relation` | ✅ 采纳 | Phase 1 新增 **dimension 表 + metric_dimension_relation**（检查意见遗漏的 dimension 实体表一并补齐），服务 Phase 5 维度合法性校验 |
| 8 | 补 `column_business_term` 字段别名表 | ❌ 不采纳 | 与既有**术语库**职责重叠（`游客量→visitor_count` 正是 terminology 职责），新建会造成术语双写。字段别名继续走术语库；必要时 `column_metadata` 加 alias 列 |
| 9 | 路线整体重排（Validator 全放 Compiler 后） | ⚠️ 折中 | Schema 提前采纳；Validator 按 #1 拆两级，告警级不后移 |

**检查意见未发现、v1.1 自查补入**：`metric_definition` 缺 oid/数据源归属（多组织/多数据源下 `source_table` 歧义、检索无法按 ds 过滤）。

## 二、目标链路（v1.1 定型）

```text
                  用户问题
                     |
                     ↓
        ┌── 数据源选择（既有 select_datasource，不动）──┐
        └──────────────────┬────────────────────────┘
                           ↓
        ┌── Query Understanding（Phase 4）──┐
        │  意图/实体/计算意图识别              │
        └──────────────┬───────────────────┘
                       ↓
              Query Plan (JSON)  ←—— pydantic 严格校验
              {intent, metrics[], dimensions[], filters[],
               time_range, calculation{type}, sub_queries[]}
                       |
      ┌────────────────┼──────────────────────┐
      ↓ (指标命中，短路)  ↓ (兜底/复杂查询)         ↓
 指标RAG(Phase 1)     术语RAG(保留)         Schema语义文档RAG(Phase 2)
      |  └── 维度合法性校验(metric_dimension_relation) ──┘
      └────────────────┴──────────────────────┘
                       ↓
          Plan 分流（Phase 5 显式规则）：
          单表聚合主干 → DSL Compiler 确定性编译
          多表join/窗口/编译失败 → 原 LLM 直出 SQL（永久回退轨）
                       ↓
   口径校验：告警级(Phase 3，全程) ｜ 阻断级(Phase 5，Plan 强绑定时启用)
                       ↓
   既有 check_sql / 表白名单 / 权限 / 执行（不动）
                       ↓
   Result Validator（Phase 3：L1 通用异常 → L2 指标 unit/范围）
                       ↓
   计算引擎（Phase 6，Post-Query，按 plan.calculation 程序化计算）
                       ↓
   既有图表生成 / 前端展示（契约不变）
```

## 三、兼容性总则（每个步骤都必须满足）

1. **配置开关**：每个 Phase 在 `backend/common/core/config.py` 新增独立开关，**默认关闭 = 行为与当前完全一致**。
2. **回退链**：DSL 轨道"plan 生成 → schema 校验 → 编译 → 规则校验"任一环节失败，自动回退原 `generate_sql` LLM 直出流程，问数不中断。
3. **数据库只增不改**：alembic 迁移只新建表，不修改/删除既有表列；可独立回滚。
4. **旧代码注释保留**：沿用 `【改造标记 XXX】` 惯例，替换段旧代码注释保留、禁止删除。
5. **前端契约不变**：SSE 消息类型与结果表结构不变；计算引擎/结果校验不新增消息类型。
6. **校验默认只观测不阻断**：Phase 3 全部校验 log-only；阻断能力（口径 enforce、结果 strict）独立开关且后置启用。
7. **新模块独立**：新 app 路由在 `apps/api.py` 注册，无路径冲突；元数据为空时检索返回空，等价未启用。

### Phase 1：指标中心 MVP（★★★★★，最高优先级）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**查什么**"——业务口径权威来源；同时补建维度模型与数据源归属（v1.1 修订 #2/#7）。 |
| **数据模型** | alembic `072_metric_center`（只增表）：<br>① `metric_definition`：metric_name/description/business_domain/**oid/specific_ds/datasource_ids（照 `terminology_model.py:14-21` 惯例）**/source_table/source_column/aggregation/filter_rule/time_field/**unit（单位）/normal_range（合理范围，JSONB）**/status/**version**。<br>② `metric_alias`（metric_id/alias）。<br>③ `metric_document`（metric_id/document_text/embedding/keyword_list 预留，可整表重建）。<br>④ **`dimension`**（共享维度实体：dimension_name/aliases(JSONB)/default_column/description/oid）。<br>⑤ **`metric_dimension_relation`**（metric_id/dimension_id/enabled）——记录指标支持/不支持的维度。<br>**元数据（Source of Truth）与检索索引分离**：口径变更→重建 document，不动业务元数据。 |
| **字段别名说明** | 字段级业务别名（`visitor_count=游客量`）**继续由既有术语库承载**，不新建 `column_business_term`，避免术语双写（修订 #8 不采纳项）。 |
| **模块** | 新建 `backend/apps/metric/`（models/curd/api，结构照抄 `terminology`）；路由注册 `apps/api.py`；前端指标管理页（参照术语管理，独立页面）。 |
| **检索** | 复用 BM25（`keyword_retrieval.py`）+ pgvector + 并入 `llm_filter_context`（`llm.py:498`）rerank；**按 oid + 数据源过滤**（与三路 filter 同参）。`keyword_list` 列预留不物化。 |
| **接入点** | `run_task`（`llm.py:1458-1465`）与无数据源分支（`llm.py:994`）新增 `filter_metric_template`；`init_messages` 注入"相关业务指标"块（**排在术语块之前**），块内含指标支持的维度列表。 |
| **元数据治理** | 辅助脚本：LLM 根据 DDL+注释+样本数据生成表/字段业务描述与指标候选，人工确认入库；**同批产出 Phase 2 所需 schema 语义文档草稿**（治理一次、两处复用）。 |
| **兼容性** | `METRIC_CENTER_ENABLED` 默认 False；False 时 filter 不执行、提示词无变化；指标库为空=召回为空。**本 Phase 不碰 SQL 生成**。 |
| **验收** | 开关关=回归与基线无差异；开关开=业务词问题提示词出现正确指标定义，准确率不降（目标提升）；多数据源环境下指标按 ds 正确隔离。 |
| **工作量** | 后端 1~2 周（含治理脚本与首批指标/维度录入）。 |

### Phase 2：Schema 语义文档 MVP（★★★★，原 Phase 6 提前，与 Phase 1 并行）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**去哪查**"。**修订 #4**：冷启动期指标覆盖率低（如 30%），大部分问题仍依赖 schema 探索——schema 检索是**主干路径**，不是兜底，故提前。 |
| **改动** | ① `table_metadata` / `column_metadata` / `schema_document`（object_type/object_id/document_text/embedding），分离同 Phase 1 模式；`column_metadata` 预留 `alias` JSONB 列（承接少量字段别名补充，**主渠道仍是术语库**）。<br>② **语义文档加工层**：替换"DDL/JSON 原样 embedding"为业务语义文本（表用途/字段中文含义/支持的分析），消除 `varchar/bigint/id` 技术噪声；文档由 Phase 1 治理脚本顺带生成。<br>③ 复用 `datasource.py:569 calc_table_embedding` 向量选表框架，仅替换 embedding 文本来源。<br>④ **指标短路**：DSL 轨道命中指标时用 `metric.source_table` 直接取表结构（现成 `get_table_schema(..., embedding=False, table_list=[...])`），跳过向量检索——**短路是加速，schema RAG 才是覆盖率保证，两者并存**。 |
| **同步** | schema 侧挂接数据源元数据同步任务（参考 `table_embedding.py:43` 批量计算）。 |
| **兼容性** | `SCHEMA_DOC_ENABLED` 默认 False = 走现有 DDL embedding 路径；两路径互为回退。 |
| **验收** | 新路径选表准确率 ≥ 旧路径；表结构变更后文档可重建；指标短路路径结果与全量检索一致。 |
| **工作量** | 1~1.5 周（与 Phase 1 并行，治理成本已摊入 Phase 1）。 |

### Phase 3：可信校验层（告警级，log-only，★★★★）

> v1.1 新增整合（修订 #1 拆分 + #6 Result Validator）。**两个子模块都只依赖 Phase 1、不依赖 Plan/DSL，对现有 LLM 轨道立即生效，因此合并为一个 Phase 且必须早做。**

#### 3-A：口径校验·告警级（问题侧弱绑定）

| 项 | 内容 |
| -- | -- |
| **绑定机制** | 不需要 Plan：Phase 1 的指标召回结果（并入 `llm_filter_context` 的命中指标）即"问题↔指标"**弱绑定**；再用 sqlglot AST 检查生成 SQL 是否涉及命中指标的表/字段，命中则应用其 `metric_rule`。 |
| **改动** | ① `metric_rule`（rule_type：required_filter/forbidden_field/forced_agg，rule_content）；② `backend/common/utils/metric_validator.py`：sqlglot AST 规则检查；③ 挂接 `llm.py:1547 check_sql` 之后。 |
| **兼容性** | `METRIC_RULE_ENFORCE` **默认 False = 仅日志告警，不阻断**。规则为空/无命中指标 = 不校验。**阻断级（Plan 强绑定）在 Phase 5 启用**（修订 #1：告警早、阻断晚，不整体后移）。 |
| **验收** | 缺 `status=1` 的 SQL 产生告警日志且执行不受影响；日志含指标名、规则、SQL 片段，可统计口径违规率。 |

#### 3-B：Result Validator（结果验证，L1 通用 + L2 指标级）

| 项 | 内容 |
| -- | -- |
| **目标** | 填补"SQL 正确 ≠ 数据正确"的结果端缺口（检查意见指出的最大遗漏）。 |
| **L1 通用校验**（不依赖元数据） | 空结果、行数超限（可配阈值）、全 NULL 列、数值量级异常（可配上限）、主键重复——**DSL 与 LLM 两条轨道共用**。 |
| **L2 指标级校验** | 依赖 Phase 1 的 `unit`/`normal_range`：如游客量结果 10 亿 → 告警"疑似单位错误/量级异常"；L2 仅在指标录入了 unit/range 时生效（数据成熟即自动启用，无额外开关）。 |
| **挂接点** | `llm.py:1619 execute_sql` 之后、`save_sql_data`（`:1629`）之前。 |
| **兼容性** | `RESULT_VALIDATOR_ENABLED` 默认 False；开启后默认仍为 **log-only**（strict 阻断模式独立配置、后置启用）。 |
| **验收** | 构造空结果/超量级用例产生告警；正常结果零打扰；前端行为无任何变化。 |
| **工作量** | 合计 1 周（3-A 3~4 天 + 3-B 3~4 天）。 |

### Phase 4：Query Plan 语义解析层（★★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"LLM 一次性任务过重"与"**计算意图放哪**"。计算意图是 Plan 字段、不是指标属性——**本 Phase 的 schema 必须一次设计到位（含计算意图与多子查询结构），执行后置到 Phase 6**（结构先行、执行后置，防返工）。 |
| **Plan 结构** | 新建 `backend/apps/chat/schemas/query_plan.py`（pydantic）：<br>`{query_type, metrics[], dimensions[], filters[], time_range{current, previous}, calculation{type, expr}, sub_queries[]}`。<br>`calculation.type`（yoy/qoq/share/growth/rank/none）决定子查询拓扑——同比展开为两个 time_range 子查询 + 比值表达式（文旅规划 Agent DAG 的退化形式）。 |
| **关于 datasource 字段（修订 #2 结论）** | **Plan 默认不携带 datasource**：现有链路 `select_datasource`（`llm.py:1486`）先于 SQL 生成执行，数据源已由链路外部确定并贯穿上下文；多来源指标的归属消歧由 `metric_definition` 的 oid/ds 字段解决。若未来出现"同一问题需跨源路由"，再扩展 `candidate_sources`（预留字段位，不在 MVP 实现）。 |
| **生成** | `generate_query_plan`：LLM 输出 JSON → pydantic 严格校验 → 落日志/前端展示；**本 Phase 不改变 SQL 生成路径**，先验证"理解"准确率。 |
| **挂接点** | `generate_sql`（`llm.py:1509`）之前插桩；失败走原逻辑，零影响。 |
| **兼容性** | `QUERY_PLAN_ENABLED` 默认 False = 不调用 plan 生成，零额外 LLM 开销。 |
| **验收** | 同比/环比/排名/趋势类问题 plan 解析正确率 ≥ 85%；**最终 SQL 与结果与 Phase 0 基线完全一致**（不改 SQL 路径）。 |
| **工作量** | 1 周。 |

### Phase 5：SQL Builder（DSL → SQL 确定性编译）+ 阻断级校验（★★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**怎么查**"：从"让 LLM 猜 SQL"变为"系统编译 SQL"。 |
| **Plan 分流规则（修订 #3 显式化）** | **Query Plan ≠ DSL**。Plan 产出后二分：<br>✅ 进 DSL Compiler：单表聚合主干（指标+维度+过滤+时间+分析类型），且全部维度通过 `metric_dimension_relation` 合法性校验；<br>❌ 进 LLM 回退轨：多表 join、窗口函数、指标不支持的维度、编译任一环节失败、plan 校验失败。<br>**不要求所有 Plan 都被编译；LLM 轨道是永久能力，不是过渡产物。** |
| **改动** | 新建 `backend/apps/chat/task/sql_builder.py`：<br>① **解析**：metric → `metric_definition`（table/column/aggregation/filter_rule/time_field，按当前 ds 过滤）；dimension → `dimension.default_column`（在 metric.source_table 中存在才用，否则分流回退）；<br>② **编译**：基于 **sqlglot AST** 组装 SELECT/WHERE/GROUP BY/时间条件/指标默认过滤，禁止字符串拼接；<br>③ **阻断级口径校验（修订 #1 落点）**：plan 强绑定存在时，`METRIC_RULE_ENFORCE=True` 才允许——此时校验"plan.metric ↔ 生成 SQL"精确对应，违规阻断；**LLM 轨道始终维持告警级**。 |
| **挂接点** | `QUERY_PLAN_ENABLED` 且 `DSL_COMPILE_ENABLED` 同时开启：plan → compile 成功 → 产物送入既有 `check_sql`（`:1547`）起的原流程（表白名单/权限/执行/图表全复用）；失败 → 原 `generate_sql`。 |
| **兼容性** | 双开关默认 False；回退链完整；`METRIC_RULE_ENFORCE` 即使 True，对无 plan 的 LLM 轨道也只降级为告警，不会误伤。 |
| **验收** | 单指标/过滤/时间/排名题走 DSL 轨道（日志可见）且结果正确率 ≥ LLM 轨道；复杂关联题全部正确回退；阻断级仅在 plan 命中时生效；整体准确率 ≥ Phase 0 基线。 |
| **工作量** | 1.5~2 周。 |

### Phase 6：计算引擎（Post-Query Calculation Engine，★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**怎么算**"：业务公式由程序计算，LLM 只做表达。 |
| **定位与三类分工（修订 #5 明确边界）** | 本引擎是 **Post Query Calculation Engine**，只做第二类：<br>**类型1 数据库计算**（sum/count/avg/group by/占比的分组聚合）→ 留在 SQL，由 Phase 5 编译进 SQL，**不进 Python**；<br>**类型2 业务公式**（同比/环比/增长率/跨期比值）→ 本引擎：按 plan 展开 N 个子查询执行后 Python 计算；<br> **类型3 统计分析**（趋势拟合/预测/异常检测）→ 不在本期，后续独立扩展（与"分析预测后置"的既定范围一致）。 |
| **改动** | 新建 `backend/apps/chat/task/calc_engine.py`：输入 `plan.calculation` + 各子查询结果，输出**合并为普通行列结构**（如 `period|value` 或 `current|previous|growth`），使 `save_sql_data`、图表生成、前端 SSE 契约**完全不变**；纯 Python 函数库（除零保护、精度约定）。 |
| **挂接点** | `execute_sql` 附近，plan.calculation 非 none 时启用；无 plan / calculation=none 走原单 SQL 执行。 |
| **兼容性** | `CALC_ENGINE_ENABLED` 默认 False；LLM 轨道（无 plan）永不触发。 |
| **验收** | "同比增长多少"结果由代码算出（日志含计算过程）且与人工核算一致；除零/空结果有确定性处理；图表正常渲染。 |
| **工作量** | 1 周。 |

## 六、开关与模式矩阵

| 开关 | 所属 Phase | 默认 | 说明 |
| ---- | ---- | ---- | ---- |
| `METRIC_CENTER_ENABLED` | 1 | False | 关=提示词无指标块 |
| `SCHEMA_DOC_ENABLED` | 2 | False | 关=走既有 DDL embedding 路径 |
| `METRIC_RULE_ENFORCE` | 3/5 | False | False=仅告警；True 且有 plan 强绑定=阻断；**True 对 LLM 轨道仍为告警** |

**运行模式**（灰度期固定为这三种组合，避免开关矩阵爆炸）：
M0 全关（= 原版 SQLBot）｜ M1 观测模式（1+2+3+4 开，校验 log-only）｜ M2 DSL 主轨（全开，LLM 轨道回退）。

## 七、风险与缓解（v1.1 更新）

| 风险 | 缓解 |
| ---- | ---- |
| DSL 通用化无底洞（join/窗口/多表） | Plan 分流规则显式化：单表聚合主干才进编译，复杂查询**永久**走 LLM 轨道 + 校验兜底 |
| 指标中心录入成本高、无人维护 | 治理脚本半自动 + 人工确认；先 Top 30 高频指标；命中率挂钩运营 |
| **术语/规则双写冲突** | 字段别名唯一入口=术语库（不建 `column_business_term`）；规则唯一入口=指标中心/校验层；Phase 7 收敛自定义 Prompt |
| 冷启动期指标覆盖不足 | Phase 2 提前 + 短路与 schema RAG 并存，覆盖率不依赖指标治理进度 |
| 过早阻断误伤 | 告警/阻断两级：全部校验默认 log-only，阻断需 plan 强绑定 + 显式开关 + 评测确认 |
| 结果校验误报 | L1 阈值可配、默认宽；L2 仅在指标录入 unit/range 后生效；均 log-only 起步 |
| 多开关组合爆炸 | 六、模式矩阵限定三种组合 |
| 计算结果破坏前端契约 | 计算引擎/结果校验输出统一行列结构，复用 `save_sql_data` 与图表生成，SSE 消息类型不新增 |
| 指标口径变更的历史数据 | `metric_definition` 带 `version`/`status`，问答记录落 plan 快照，可追溯当时口径 |

---

## 八、一句话总结

> 按 **评测基线 → 指标中心（含维度/归属）∥ Schema 语义文档 → 可信校验层（告警级）→ Query Plan → SQL Builder（双轨+阻断级）→ 计算引擎 → 灰度切换**
> 八步推进；每步独立开关、只增表不改链、校验先观测后阻断、DSL 轨道全程可回退 LLM 轨道，
> 最终把 SQLBot 从「RAG 增强 Text2SQL」升级为「**Metric + DSL 驱动的可信问数系统**」。
