# 薄插桩（thin instrumentation / 薄探针）
> 你的理解**方向是对的**：把横切逻辑抽出去，主流程只保留一行调用，减少主业务代码膨胀。但要区分：**薄插桩核心目标不是简化业务逻辑，而是插入「轻量的观测/埋点/校验逻辑」，不侵入业务本身**。

## 一句话定义
**薄插桩：在业务流程入口/出口，插入一段极简、低开销的探针代码（桩代码）；桩只做观测、埋点、计时、权限校验，不修改原有业务主逻辑。桩代码尽量薄，只做转发/采集，不写复杂业务。**

> 对应你SQLBot场景：
> 主链路：用户问题 → RAG检索 → LLM重排 → 生成DSL → SQL → 执行
> 薄插桩就是：在每个阶段的**入口、出口**加一行桩调用，用来记录耗时、入参、结果、异常，**不改动原有业务分支**。

## ✅ 你说的这一点：封装逻辑、简化主流程
典型对比：
**【不做薄插桩：业务主流程里混杂埋点】**
```python
def query_flow(question):
    # 业务前，混杂一堆埋点代码（主流程被污染，很长）
    start = time.time()
    trace_id = gen_trace()
    logger.info(...)
    try:
        # 核心业务
        candidates = bm25_retrieve(question)
        filtered = llm_rerank(candidates, question)
        dsl = llm_generate_dsl(question, filtered)
        sql = dsl_parser(dsl)
        res = db.execute(sql)
    except Exception as e:
        logger.error(...)
        span.set_exception(e)
        raise
    # 后置埋点
    span.end()
    logger.info("耗时", time.time()-start)
    return res
```

**【薄插桩改造后】**
```python
@thin_instrument("sqlbot_query_flow") # 薄插桩装饰器，一行
def query_flow(question):
    # 主流程干干净净，只剩下业务核心
    candidates = bm25_retrieve(question)
    filtered = llm_rerank(candidates, question)
    dsl = llm_generate_dsl(question, filtered)
    sql = dsl_parser(dsl)
    res = db.execute(sql)
    return res
```
`thin_instrument` 这个装饰器就是**薄桩**：
内部自动处理：trace生成、计时、日志、异常捕获、指标上报。
**业务代码完全不用关心埋点逻辑。**

## 薄插桩 vs 厚插桩（重点区分）
1. **薄插桩（thin）**
- 桩代码**只做观测、采集、指标、日志、简单前置拦截（权限）**
- 几乎不改变业务输入输出；**不修改业务结果**
- 执行开销极小；失败可以降级（桩报错不阻断主业务）
- 代码形态：装饰器、AOP切面、方法前后的极简钩子
> 适合：链路追踪、耗时统计、日志埋点、简单权限校验，**就是你SQLBot需要的可观测埋点**

2. **厚插桩（thick / heavy instrumentation）**
- 桩内部包含大量业务改写、替换、复杂转换
- 会修改入参、替换返回值、替换底层函数实现
- 一旦桩出错，业务直接不可用
> 例如：动态替换函数、修改DSL结构、改写SQL，属于厚插桩

## 薄插桩的设计规则（薄插桩规则）
1. **桩只做横切关注点，不承载业务逻辑**
业务逻辑（BM25检索、LLM重排、DSL生成）不能写进桩代码。桩不能决定召回哪些术语，不能修改LLM的prompt。
2. **桩必须轻量化**
桩内部逻辑尽量短，避免复杂计算；桩本身耗时要远小于业务本身。
3. **桩故障不阻断主业务（熔断降级）**
埋点/日志上报失败，**不能让SQL问答流程抛异常**。
4. **桩与业务解耦，可开关**
可以配置全局开关，一键关闭所有薄插桩，业务代码完全不变。
5. **只在边界点插入**
只在函数入口、出口；不要在业务循环、复杂分支内部到处插桩。
> 边界：`query_flow`、`bm25_retrieve`、`llm_rerank`、`dsl_parser` 这些函数的出入口。

## 和你SQLBot架构的结合
你的链路每个模块，都适合薄插桩：
- `bm25_retrieve`：桩记录召回数量、检索耗时、检索关键词
- `llm_rerank`：桩记录候选数量、重排前后id列表、token消耗、耗时
- `llm_generate_dsl`：桩记录DSL原始输出、解析是否成功
- `dsl_parser`：桩记录生成SQL、校验结果

> 好处：主业务代码保持干净，所有观测埋点全部抽离到薄插桩AOP。后续新增指标，**不用修改业务主流程代码**，只修改桩的实现。

## 容易混淆的概念
1. 薄插桩 ≠ 重构业务逻辑
> 它**不是用来重构业务**，只是在业务边界插入观测/轻量拦截。不要把业务判断写到桩里面。
2. 薄插桩 ≠ 静态代码插桩（字节码插桩）
> 薄插桩可以是源码层AOP/装饰器（Python最常用），不一定需要字节码、二进制插桩。

## 一句话总结你的理解修正版
> 薄插桩，是在业务方法的边界，封装**观测类横切逻辑**，用一行调用注入，从而让主业务代码只保留核心业务，不混杂埋点、计时、日志等非业务代码；桩本身尽量轻量化，不修改业务结果。
