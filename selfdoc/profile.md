# 用户使用风格画像

> 创建时间：2026-10-13
> 来源：基于 sqlbot_pro v201 改造期间多次交流的观察总结。
> 用途：供 AI 助手理解用户协作偏好，对齐工作方式；用户审阅确认版。

---

## 一、节奏控制：行动前必须"先对齐、后动手"

- **分析与修改严格分阶段**：多次明确「先不要修改任何代码和文件」「仅作讨论」——目的是**达成一致后再动手**，而不是让助手边猜边改。
- **方案审阅制**：关键改动会要求「你说下实施方案，我先看下，然后你再处理」——方案过目认可 = 动手许可。
- **拍板干脆**：对齐后决策极简，常以编号形式给出（「1、采用 column_name。2、治理脚本的作用是什么」），不拖泥带水。
- **会话节奏自主掌控**：「下午再说吧，我先去吃饭啦」——该停即停，上下文由助手负责挂住。

## 二、问题意识：自带一手观察，用事实说话

- **不抛模糊 bug，直接给现象 + 自查证据**：如「每次编辑维度，数据源和数据表信息都没了。我查看数据库中的维度表发现，根本没有数据源及数据表字段」——现象、操作路径、DB 验证三要素齐全。
- **先定性再问方案**：自己完成初步归因（"数据库里根本没有这个字段"），把讨论推进到"该怎么办"而非"是什么"。

## 三、思维方式：第一性原理 + 务实，反感绕弯

- **用真实世界常识挑战设计抽象**：「真实的 IT 系统，从没有什么默认的字段名，开发人员建表都有自己的规范」——一句话否定"默认值"式设计。
- **敏锐识别答非所问**：「我感觉你的方案一直不在问题本身，而是一直说当前不用改，用 LLM 兜底」——对"回避型答案"零容忍，要求直面问题本身。
- **反感人为复杂化**：「你越来越偏离问数本身了，本来是一个维度与表的关联问题，你把它说得越来越复杂」——期望**方案复杂度与问题复杂度匹配**，讨论发散时会被叫停。
- **质疑看似权威的依据**：「评测数据无法覆盖真实场景，存量场景有限，持续出现的新场景无法被评测数据框定」——推翻"等 Phase 0 数据裁决"的决策链，要求重新推演。
- **会用复述确认理解**：「你的意思是……让 LLM 根据表结构自主处理字段名问题？」——通过复述校准对方表达的本意，助手需给出准确的"对/不对 + 修正"。

## 四、决策与执行风格

- **全局一致性优先**：「数据治理脚本要和前后端链路的维度数据表保持一致」——不允许局部方案破坏系统整体口径统一。
- **分级处理问题**：能立刻做的拍板立刻做；暂不做的「先记下来」（如治理脚本易用性 → 记入问题文档待决策），**不把待办和行动混在一起**。
- **命名等细节亲自定夺**：字段叫 `column_name` 还是保留 `default_column` 由用户拍板，不接受助手替其默认。
- **验证闭环**：改动后亲自 UI 走查 + 查库核对，验证通过才进入下一议题（「验证通过。我们讨论一个问题」）。

## 五、对 AI 助手的隐性要求

| 要求 | 反面教材（会被批评） |
| ---- | ---- |
| 方案贴着问题本身 | 发散到评测方法论、累积经济学等无关层面 |
| 结论明确、敢于给答案 | 「当前不用改，LLM 兜底」式回避 |
| 尊重阶段门控 | 未经许可改文件 |
| 简洁直接 | 冗长铺垫、过度解释 |
| 诚实标注边界 | 把讨论中的"演进方向"说成"必须现在做的" |

---

**一句话总结**：用户是**"强事实输入、强决策控制、反感发散与回避"**的协作风格——先给现象与证据，要求方案对齐问题、复杂度匹配、全局一致，审阅后快速拍板，执行后亲自验证闭环。
