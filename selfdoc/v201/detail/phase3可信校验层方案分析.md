# Phase 3 可信校验层 方案分析

> 创建时间：2026-10-16｜定位：实施前目的梳理（用户要求"先梳理目的、再出实施方案"）。
> 配套：权威规格《v201改造方案_v1.2.md》第四节 Phase 3 章节；全局规则 G1~G5（同文档第三节）；讨论结论 3.4-5 见《v201的改造问题发现与分析处理.md》。
> 状态：**已验收闭环（实施 2026-10-16；C1~C3 用户走查通过 2026-10-20——实施与验收记录见《v201的改造进展情况.md》第六节）**。目的分析与实施边界以本文档为准。

## 1. 一句话定位

给现有 LLM 直出 SQL 的链路加一层**"旁路仪表"**：SQL 生成后、执行前后各做一轮确定性校验，发现可疑就**记告警日志**——不阻断、不改结果、前端零感知（log-only）。

## 2. 为什么需要：NL2SQL 的真实风险是"静默错误"

SQLBot 现状链路：LLM 生成 SQL → `check_sql`（`apps/chat/task/llm.py:check_sql`，表名白名单等安全性检查）→ 执行 → 存结果。`check_sql` 挡住的是**危险**（注入、越权表），挡不住**错误**：

| 静默错误类型 | 例子 | 现状后果 |
|---|---|---|
| 口径漂移 | 问"游客量"，SQL 漏了指标要求的日期过滤/错误聚合方式 | 数字看着合理，口径错了，没人知道 |
| 结果异常 | 筛选条件过严 → 空结果；单位混用（万元/元）→ 量级差一万倍 | 用户要么困惑要么误信 |
| 表述与数据不符 | LLM 用了不存在/不相干的字段逻辑 | 事后极难排查 |

这类问题的共同点：**不报错、不崩溃，只是悄悄给出错的东西**。问数产品最大的信任风险恰恰在此。Phase 3 的目的就是把"静默"变"可观测"——这是 G4「先观测后阻断」的前半句：**没有观测数据，永远没有依据决定该不该阻断、在哪阻断**。

## 3. 链路位置与两个子模块

```
LLM 生成 SQL ──→ [3-A 口径校验] ──→ check_sql ──→ 执行 ──→ [3-B Result Validator] ──→ 存结果/前端
                  （执行前·静态 AST）                              （执行后·结果检查）
```

一前一后夹住 SQL 生命周期：3-A 管"生成得对不对"（执行前，静态分析 SQL 文本）；3-B 管"结果可不可信"（执行后，动态检查结果集）。

## 4. 3-A：口径校验·告警级（问题侧弱绑定）

- **绑定机制**：不需要等 Phase 4 的 Plan——Phase 1 指标召回的命中结果本身就是"问题↔指标"的**弱绑定**（本次问数大概率在算哪些指标已知）；用 sqlglot 解析生成 SQL 的 AST，检查是否涉及命中指标的表/字段，涉及则加载该指标的规则做校验。
- **规则来源**：新表 `metric_rule`（`rule_type`：`required_filter` 必带过滤 / `forbidden_field` 禁用字段 / `forced_agg` 强制聚合方式；`rule_content` 具体内容）——由管理端/治理脚本录入，指标录完规则即生效。
- **顺带优先做的硬底线**（讨论结论 3.4-5，2026-10-13）：**列存在性/类型校验**——表结构是已知的，SQL 引用的列是否存在、类型是否可比，是**零配置、100% 可判定**的检查，对 LLM 轨道同样适用，是开放场景下最便宜的确定性保障，Phase 3 明确优先做这类。
- **挂接点**：`llm.py` 中 `check_sql` 之后（`check_save_sql`/`run_task` 内调用处），薄插桩一行调用；实现落 `common/utils/metric_validator.py`（G1 薄插桩：`llm.py` 只加调用与开关判断）。

## 5. 3-B：Result Validator（L1 通用 + L2 指标级）

- **L1 通用检查**（与指标无关，DSL/LLM 两轨将来共用）：空结果、行数超限（可配）、全 NULL 列、数值量级异常（可配上限）、主键重复。
- **L2 指标级检查**：吃 Phase 1 已预留的 `unit`/`normal_range` 字段——如"游客量"正常区间几十万，结果出来 10 亿 → 告警疑似单位/量级错误。**指标录入即自动生效，无需额外配置**（Phase 1 的数据铺垫在此兑现）。
- **L3 业务一致性**（总量 vs 分项加总，如全市 100 万 ≠ 各区加总）：`additivity` 字段 Phase 1 已预留，但本项**显式标注不做**（G5：预留≠实现），只留演进位置。
- **挂接点**：`execute_sql` 之后、`save_sql_data` 之前——校验只读结果集，不改写、不丢弃。
- **两轨共用**（G2）：设计为 DSL/LLM 通用，Phase 5 DSL 轨道启用时直接复用。

## 6. 为什么必须 log-only（G4 + G2 的落地）

- **G4 先观测后阻断**：阻断需"强绑定 + 显式开关 + 评测确认"三者齐备——当前规则是弱绑定（召回命中而非 Plan 精确绑定）、Phase 0 评测基线未跑，三缺其三，**只配观测不配阻断**；
- **G2 双轨永久**：LLM 轨道上任何校验只降级不误伤——误拦一个正常问题的代价远大于漏记一条告警；
- **演进路径**：Phase 3 告警日志积累"哪些规则被频繁违反、误报率多少"的数据 → Phase 5 才有依据把个别强规则升为阻断级（`METRIC_RULE_ENFORCE` 届时才谈 enforce=True）。**Phase 3 是给 Phase 5 修路的，不是现在就执法。**

## 7. 时机论证（为什么 Phase 1 之后、Phase 4/5 之前做）

| 维度 | 论据 |
|---|---|
| 依赖 | 只依赖 Phase 1（指标中心提供规则锚点 + `unit`/`normal_range`），不依赖 Plan/DSL → 不必等 Phase 4/5 |
| 立即生效 | 对现有 LLM 轨道当天生效——指标召回（Phase 1 已上线）+ 校验告警 = 观测闭环，不用等新架构 |
| 数据价值 | 告警日志同时喂给：Phase 0 评测（违规率进基线报告）、Phase 4 confidence 调参、Phase 5 阻断决策 |
| 规格原话 | "两个子模块都只依赖 Phase 1、不依赖 Plan/DSL，对现有 LLM 轨道立即生效，**必须早做**"（v1.2 Phase 3 引言） |

## 8. 边界（本期明确不做）

1. **不阻断**：一切告警旁路，SQL 照常执行、结果照常返回；
2. **前端零变化**：告警只进后端日志，SSE 契约不动；
3. **strict 模式后置**：`RESULT_VALIDATOR_ENABLED` 开启后默认仍 log-only，strict 独立配置留后；
4. **L3 一致性校验不做**（演进项，G5）；
5. **不碰 SQL 生成路径本身**：校验全在旁路，开关关 = 与原版逐字一致（兼容性总则）。

## 9. 验收标准（规格收敛）

- **3-A**：构造违规 SQL（如漏 `required_filter`）→ 产生告警日志、执行不受影响；日志含**指标名/规则/SQL 片段**，可统计违规率；
- **3-B**：构造异常结果用例（空结果/量级异常）→ 产生告警；正常结果零打扰；前端无变化。

## 10. 工作量与开关

- **工作量**：规格估 1 周（3-A 3~4 天 + 3-B 3~4 天）；
- **开关**：`METRIC_RULE_ENFORCE`（默认 False = 仅告警，阻断级 Phase 5 再谈）、`RESULT_VALIDATOR_ENABLED`（默认 False；开启后默认 log-only，strict 后置）。
