# SQLBot 企业级问数改造方案 v1.2（最终版，分步实施）

> 基于《v201改造方案_v1.1.md》与《v201改造方案v11的检查意见.md》的逐条评估收敛而来。
> 核心目标不变：将 SQLBot 从「RAG 增强型 Text2SQL」升级为「**Metric + DSL 驱动的企业级查询系统**」，
> **每个阶段完成后系统直接可运行**，后续阶段逐步叠加。
>
> v1.2 定位：**架构冻结版**。本轮修订全部为字段级/规则级微调，不再改动阶段结构与依赖骨架；
> 后续只做三个实施设计（Query Plan JSON Schema、Metric Center ER、DSL 语法与 Compiler 实现方案）。

## 〇、v1.1 → v1.2 修订说明

| # | 检查意见（v11） | 采纳 | v1.2 落点与修正 |
| - | ---- | ---- | ---- |
| 1 | Plan 增加 datasource extension point | ✅ 字段级采纳 | `sub_queries[].datasource_id: Optional[int]` 仅 schema 预留；**执行能力（多连接/结果合并/跨源权限）明确不在本期**，文档两处注明 |
| 2 | `metric_type`（atomic/derived/composite）+ Metric DAG | ⚠️ 修正采纳 | 加 `metric_type` 字段 + `metric_dependency` **只建表不实现编译展开**；**补仲裁规则**（检查意见遗漏）：指标中心命中预定义派生指标 → 用固化口径；未命中 → `plan.calculation` 临时计算，杜绝双口径 |
| 3 | schema_document 分 TABLE/COLUMN 两级 | ✅ 确认项显式化 | 意见自相矛盾（又列建议又承认已有）——v1.1 `object_type/object_id` 本就是多粒度设计，仅显式写明取值含 `COLUMN` |
| 4 | Plan 增加 confidence/ambiguity 澄清 | ⚠️ 修正采纳 | 字段照加；**第一版仅做"低置信提示"不做多轮追问**（前端+会话状态不在本期）；置信度混合召回信号（top1/top2 分差、命中数），不单信 LLM 自报；阈值靠 Phase 0 评测集调参 |
| 5 | Result Validator 补 L3 业务一致性 | ✅ 采纳（演进项） | L3 标注未来；**补检查意见遗漏的前置**：`metric_definition` 本批就加 `additivity` 字段（可加/半可加/不可加），避免 L3 上线时回头改表 |
| 6 | 计算引擎演进为 Calculation Planner（SQL/Python 双后端） | ✅ 演进注记 | 不实现；注记中补**双后端一致性回归测试**成本 |
| 7 | Semantic Layer Runtime（`apps/semantic/`） | ✅ 本轮最有价值 | 落地修正：不在 Phase 1 建 facade（过早抽象），而是立硬规则——**`run_task` 只允许薄插桩，业务实现一律独立模块**；Phase 4/5 时机成熟再收敛 `resolve_*/validate_*` 统一入口 |
| 8 | Plan 提前到 Phase 1 后 | ❌ 保持原序 | 它自己承认"不是必须"。依赖分析：plan 验收依赖指标召回质量（指标未录入则 metrics 全靠 LLM 猜）；提前与上一轮"Schema 提前"冲突。**吸收为：Phase 4 与 Phase 2 同只依赖 Phase 1，可并行** |

**检查意见未覆盖、v1.2 自补**：① 派生指标与 plan.calculation 仲裁规则（#2）；② confidence 校准与澄清前端成本（#4）；③ additivity 前置字段（#5）；④ 跨源"预留字段≠可执行"的边界声明（#1）。

## 三、全局设计规则（v1.2 新增，所有 Phase 共同遵守）

**规则 G1：薄插桩规则（修订 #7，防 `llm.py` 巨石化）**
`chat/task/llm.py` 及 `run_task` **只允许出现插桩调用**（形如 `metric_ctx = filter_metric_template(...)`），任何业务实现必须落在独立模块（`apps/metric/`、`apps/semantic/`、`common/utils/*`）。评审每个 Phase 的 diff 时检查：`llm.py` 新增行数应仅为调用与开关判断。Phase 4/5 落地时，将 `resolve_metric/resolve_dimension/resolve_schema/validate_*` 收敛为统一入口（`backend/apps/semantic/` facade），此前不提前抽象。

**规则 G2：双轨永久原则**
DSL 主轨 + LLM 回退轨并存，LLM 轨道不是过渡产物；任何校验对 LLM 轨道只降级（告警）不误伤。

**规则 G3：口径唯一来源**
- 字段级业务别名 → 唯一入口=**术语库**（不建 `column_business_term`）；
- 指标口径（含预定义派生指标）→ 唯一入口=**指标中心**；
- 临时计算意图 → 唯一入口=**plan.calculation**；
- 仲裁规则：**指标中心命中预定义派生指标 → 用固化口径展开；未命中 → plan.calculation 临时计算**。同一次问答不允许两处同时定义同一计算。

**规则 G4：先观测后阻断**
所有校验默认 log-only；阻断需"强绑定 + 显式开关 + 评测确认"三者齐备。

**规则 G5：预留≠实现**
任何 extension point（如 `datasource_id`）只保证 schema 前后兼容，其执行能力必须在所属 Phase 显式声明"不在本期"，防止评审误判范围。

**兼容性总则**（沿袭 v1.1，略作合并）：开关默认关=与原版行为一致；回退链完整；alembic 只增不改可回滚；旧代码注释保留；前端 SSE 契约不变；新模块路由在 `apps/api.py` 注册无冲突。

### Phase 3：可信校验层（告警级，log-only，★★★★）

> 两个子模块都只依赖 Phase 1、不依赖 Plan/DSL，对现有 LLM 轨道立即生效，**必须早做**。

#### 3-A：口径校验·告警级（问题侧弱绑定）

| 项 | 内容 |
| -- | -- |
| **绑定机制** | 不需要 Plan：Phase 1 指标召回命中结果即"问题↔指标"弱绑定；sqlglot AST 检查生成 SQL 是否涉及命中指标的表/字段，命中则应用其 `metric_rule`。 |

#### 3-B：Result Validator（L1 通用 + L2 指标级）

| 项 | 内容 |
| -- | -- |
| **L1 通用** | 空结果、行数超限（可配）、全 NULL 列、数值量级异常（可配上限）、主键重复——DSL 与 LLM 两轨共用。 |

| **兼容性** | `RESULT_VALIDATOR_ENABLED` 默认 False；开启后默认 log-only（strict 独立配置、后置启用）。 |
| **验收** | 构造异常用例产生告警；正常结果零打扰；前端无变化。 |
| **工作量** | 合计 1 周（3-A 3~4 天 + 3-B 3~4 天）。 |

### Phase 4：Query Plan 语义解析层（★★★★★，与 Phase 2 可并行）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"LLM 任务过重"与"**计算意图放哪**"；**schema 一次设计到位（含计算意图、多子查询、置信度、扩展点），执行后置 Phase 6**（结构先行、执行后置）。 |
| **Plan 结构（v1.2 完整版）** | 新建 `backend/apps/chat/schemas/query_plan.py`（pydantic）：<br>`{query_type, metrics[], dimensions[], filters[], time_range{current,previous}, calculation{type,expr}, sub_queries[{..., datasource_id: Optional[int]}], confidence{metric_confidence: float}, ambiguity{need_clarification: bool, reason: str}}`。<br>• `calculation.type`（yoy/qoq/share/growth/rank/none）决定子查询拓扑（同比=两个时间窗+比值表达式）。<br>• **`datasource_id` 仅 schema 预留**：当前由 `select_datasource`（`llm.py:1486`）在 plan 前确定，plan 不读取；跨源执行（多连接/结果合并/跨源权限）**明确不在本期（规则 G5）**，未来用于"游客量+酒店入住率"类跨源子查询。<br>• **`confidence/ambiguity`（修订 #4）**：混合信号计算——LLM 自报分 × 指标召回 top1/top2 分差 × 命中数量，不单信 LLM 自报；**本期仅实现"低置信提示"**（结果附注"存在多个可能理解：已按 A 处理，如需 B 请追问"），**多轮澄清交互（前端+会话状态）单独立项，不在本期**；阈值由 Phase 0 评测集调参。 |
| **生成** | `generate_query_plan`：LLM 输出 JSON → pydantic 严格校验 → 落日志/前端展示；**本 Phase 不改变 SQL 生成路径**。 |
| **挂接点** | `generate_sql`（`llm.py:1509`）之前插桩（薄插桩，G1）；失败走原逻辑。 |
| **兼容性** | `QUERY_PLAN_ENABLED` 默认 False = 零额外 LLM 开销。 |
| **验收** | 同比/环比/排名/趋势 plan 解析正确率 ≥85%；多义词用例触发 `ambiguity` 标记；**最终 SQL 与结果与基线完全一致**（不改 SQL 路径）。 |
| **工作量** | 1~1.5 周（schema+提示词+校验+混合置信度信号）。 |

---

### Phase 5：SQL Builder（DSL → SQL 确定性编译）+ 阻断级校验（★★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**怎么查**"：从"让 LLM 猜 SQL"变为"系统编译 SQL"。 |
| **Plan 分流规则（显式化）** | **Query Plan ≠ DSL**。二分：<br>✅ 进 Compiler：单表聚合主干（指标+维度+过滤+时间+分析类型）且维度通过 `metric_dimension_relation` 合法性校验、指标仲裁后为 atomic 或本期可展开类型；<br>❌ 进 LLM 轨道：多表 join、窗口函数、不支持的维度、derived 指标 DAG 展开（本期不支持）、编译/校验任一失败。<br>**不要求所有 Plan 被编译；LLM 轨道是永久能力。** |
| **DSL 形态约束** | DSL 保持**业务级**（`{metric, dimensions, filters, time_range, calculation}`），**不设计成 SQL AST**；sqlglot AST 只存在于 Compiler 内部。 |
| **改动** | 新建 `apps/chat/task/sql_builder.py`（G1 独立模块）：<br>① 解析：metric → `metric_definition`（按当前 ds 过滤）；dimension → `dimension.default_column`（存在于 metric.source_table 才用，否则分流回退）；<br>② 编译：**sqlglot AST 组装**（禁止字符串拼接），复用 `extract_tables_from_sql` 等既有工具；<br>③ **阻断级口径校验**：`METRIC_RULE_ENFORCE=True` 且 plan 强绑定存在时违规阻断；**LLM 轨道始终告警级**（G4）。 |
| **挂接点** | `QUERY_PLAN_ENABLED` ∧ `DSL_COMPILE_ENABLED`：plan → compile 成功 → 产物送入既有 `check_sql`（`:1547`）原流程（白名单/权限/执行/图表全复用）；失败 → 原 `generate_sql`。 |
| **兼容性** | 双开关默认 False；回退链完整；enforce=True 对无 plan 的 LLM 轨道自动降级为告警。 |
| **验收** | 单表聚合题走 DSL 轨道（日志可见）且正确率 ≥ LLM 轨道；复杂题全部正确回退；阻断级仅在 plan 命中时生效；整体 ≥ 基线。 |
| **工作量** | 1.5~2 周。 |

---

### Phase 6：计算引擎（Post-Query Calculation Engine，★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**怎么算**"：业务公式由程序计算，LLM 只做表达。 |
| **定位与三类分工** | **Post Query Calculation Engine**，只做第二类：<br>**类型1 数据库计算**（sum/count/avg/group by）→ 留在 SQL，Phase 5 编译，不进 Python；<br>**类型2 业务公式**（同比/环比/增长率）→ 本引擎：plan 展开 N 个子查询执行后 Python 计算；<br>**类型3 统计分析**（拟合/预测/异常）→ 不在本期。 |
| **演进注记（修订 #6）** | 未来大数据量下演进为 **Calculation Planner**：按数据源能力（窗口函数/条件聚合可用性）选择 SQL 后端或 Python 后端；**届时必须补双后端一致性回归测试**（同一问题两后端结果一致），纳入评测集。本期不实现（规则 G5）。 |
| **改动** | `apps/chat/task/calc_engine.py`：输入 `plan.calculation`+子查询结果，输出**合并为普通行列结构**，`save_sql_data`/图表/SSE 契约完全不变；纯 Python 函数库（除零保护、精度约定）。 |
| **挂接点** | `execute_sql` 附近，calculation 非 none 时启用；无 plan 永不触发。 |
| **兼容性** | `CALC_ENGINE_ENABLED` 默认 False。 |
| **验收** | "同比增长多少"由代码算出（日志含过程）且与人工核算一致；除零/空结果确定性处理；图表正常。 |
| **工作量** | 1 周。 |

## 六、开关与模式矩阵

## 七、风险与缓解（v1.2 更新）

| 风险 | 缓解 |
| ---- | ---- |
| DSL 通用化无底洞 | Plan 分流规则显式化：单表聚合主干才编译，复杂查询**永久**走 LLM 轨道 |
| **派生指标与 plan.calculation 双口径冲突**（v1.2 新增） | 规则 G3 仲裁：指标中心命中→固化口径；未命中→临时计算；同一问答不允许两处定义 |
| 指标录入成本高、无人维护 | 治理脚本半自动+人工确认；先 Top 30 高频指标；命中率挂钩运营 |
| 术语/规则双写 | G3：字段别名唯一入口=术语库；规则唯一入口=指标中心/校验层；Phase 7 收敛 Prompt |
| **confidence 不可校准、澄清成本被低估**（v1.2 新增） | 混合召回信号非 LLM 自报；本期仅低置信提示，多轮澄清单独立项；阈值靠评测集 |
| 冷启动指标覆盖不足 | Phase 2 提前 + 短路与 schema RAG 并存 |
| 过早阻断误伤 | G4：默认 log-only，阻断需强绑定+开关+评测确认三齐 |
| 结果校验误报 | L1 阈值可配默认宽；L2 依赖 unit/range 录入；均 log-only 起步 |
| **预留字段被误读为已支持跨源**（v1.2 新增） | 规则 G5：`datasource_id` 所在 Phase 显式声明"执行能力不在本期" |
| **`llm.py` 继续膨胀成超级文件**（v1.2 新增） | 规则 G1：薄插桩硬规则 + Phase 7 facade 收敛 + diff 评审检查行数 |
| 多开关组合爆炸 | 六、三种模式矩阵 |
| 计算结果破坏前端契约 | 输出统一行列结构，复用既有执行/图表/SSE，消息类型不新增 |
| 指标口径变更的历史数据 | `version/status` + 问答记录落 plan 快照，可追溯当时口径 |

## 九、一句话总结

> 按 **评测基线 → 指标中心（含维度/类型/归属）∥ Schema 语义文档（TABLE/COLUMN 双粒度）→ 可信校验层（告警级）→ Query Plan（含置信度/扩展点）∥ Schema → SQL Builder（双轨+阻断级）→ 计算引擎 → 灰度切换**
> 八步推进；五条全局规则（薄插桩/双轨永久/口径唯一/先观测后阻断/预留≠实现）兜底；
> 每步独立开关、只增表不改链、校验先观测后阻断、DSL 轨道全程可回退 LLM 轨道，
> 最终把 SQLBot 从「RAG 增强 Text2SQL」升级为「**Metric + DSL 驱动的可信问数系统**」。
