## 问题 1：指标管理页出现两处入口

### 现象

左侧菜单中「指标管理」既作为**独立顶层菜单项**出现一次，又出现在「设置」子菜单内一次，共两处。预期：仅出现在「设置」菜单下面。

### 原因分析（代码定位）

- `/set/metric` 是 `/set` 的子路由（`frontend/src/router/index.ts:152`），会正常进入「设置」子菜单，此为预期入口；
- 顶层菜单过滤器 `Menu.vue` 的 `routerList`（`frontend/src/components/layout/Menu.vue:47-70`）对 `/set/*` 子路由采用**排除法**：`professional / training / prompt / permission / member` 均被显式排除（`:53-58`），防止它们既出现在顶层又出现在设置子菜单；
- 新增的 `metric` **未加入该排除列表**，而 `/set/metric` 路径含 `set` 且 isSpaceAdmin 命中 `:66` 的纳入条件 → 被渲染为独立顶层菜单项，造成重复。

> 该现象即《v201的改造进展情况.md》第六节遗留项 **#2**（当时预判"倾向直接显示"，实际验证发现会重复出现两处，结论修正为：需排除顶层、仅保留在设置子菜单内）。

### 处置方案（已决策 ✅）

在 `Menu.vue` 的路径排除列表（`:53-58` 一带）增加一行：

```ts
!route.path.includes('metric') &&
```

- 效果：顶层菜单不再渲染「指标管理」，仅保留「设置」子菜单内入口；
- 影响面：仅 `Menu.vue` 一处，纯前端展示逻辑；
- 与遗留项 #1（xpack `generateRouters` 是否 removeRoute `/set/metric`）无关，该项仍按原计划上线验证。

**实施记录（2026-10-10）**：已在 `Menu.vue:58-60` 按上述方案加入排除行（带 `【改造标记 METRIC-CENTER】` 注释）；`npm run build`（vue-tsc 类型检查 + vite 构建）通过；**顶层菜单/设置子菜单 UI 走查验证通过（2026-10-10，顶层仅剩设置子菜单入口）**。

## 问题 2：表单字段与数据源/数据表无联动

### 现象

指标管理页填写指标/维度时，与物理表强相关的字段全部为自由文本输入，用户手敲表名/列名易错，且与数据源无任何关联：

| 字段 | 位置（`views/system/metric/index.vue`） | 现状 |
| ---- | ---- | ---- |
| `source_table` | :920-926 | el-input 自由文本 |
| `source_column` | :927-933 | el-input 自由文本 |
| `time_field` | :936-942 | el-input 自由文本 |
| 维度 `default_column` | :1180-1185 | el-input 自由文本 |
| `aggregation`（附带发现） | :904-910 | el-input 自由文本 |

> ⚠️ 本表维度行及下文③「弱联动不强绑」的原始方案**已被问题 4 修订**：维度改为落点三元组持久化（数据源/表/字段），`default_column` 改名 `column_name`。

### 分析

1. **接口是现成的，无需新后端接口**（`frontend/src/api/datasource.ts`）：
   - 数据源：`list()`（:10，页面已加载用于筛选）；
   - 表：`tableList(id)`（:20）/ `getTables(id)`（:13）；
   - 字段：`getFields(id, table_name)`（:15-16）/ `fieldList(ds_id, id, ...)`（:21-22）。
2. **数据模型缺口**：`metric_definition` 只有 `datasource_ids`（适用范围，可多选/全选），**没有字段记录 `source_table` 归属哪个数据源**——联动必须先确定"表所在的数据源"才能枚举表。
3. **纯下拉会锁死三类场景**：治理脚本（`metric_governance.py`）导入的历史值、跨数据源同名表/列、数据源暂时不可达时的编辑。

### 处置方案（已决策 ✅，用户拍板）

**① 数据源归属：采用方案 A——新增 `source_ds_id` 字段**

- 迁移：新开 alembic 迁移（如 `073_metric_source_ds`），**只增列**，符合"alembic 只增不改"总则；可回滚（drop column）。
- 同步改动面：`models/metric_model.py`、`curd/metric.py`（创建/更新/查询）、`api/metric.py`、前端表单与列表、治理脚本 `metric_governance.py`（生成时本就按 ds 产出，天然带 ds_id）。
- 备选方案 B（不加字段、用 `datasource_ids[0]` 推断/临时选源）**已否决**：语义含糊，Phase 5 编译取表结构时无法确定数据源。

**② 交互：级联下拉 + `filterable` + `allow-create`（或"下拉/手动输入"切换）**

- 联动链：**数据源 → 表（`source_table`）→ 字段（`source_column`、`time_field`）**；
- `source_column`、`time_field` 依赖 `source_table`，切换表后清空并校验；
- `allow-create` 兜底，保证存量数据/特殊场景可编辑。

**③ 联动范围（第三点用户已赞同）**

| 字段 | 处理 |
| ---- | ---- |
| 指标 `source_table` | 数据源→表 二级级联 |
| 指标 `source_column`、`time_field` | 选定表后字段级联 |
| 维度 `default_column` | **弱联动**：可搜索候选 + 允许自由输入（维度跨表复用，不强绑某张表，理由见第四节） |
| `aggregation` | 顺带改固定下拉（sum/count/avg/max/min…，allow-create 兼容存量） |

**④ 校验建议（实施时参考）**

- 前端：选定数据源后校验表存在、选定表后校验列存在，允许手动覆盖；
- 后端 create/update 可做软校验（管理端录入问题，与问数链路的 G4 告警规则无直接关系，但建议沿用"先告警不阻断"思路，避免治理脚本批量导入被卡）。

## 问题 4：维度编辑后数据源/数据表信息丢失

### 现象

维度管理页每次点击编辑，进入维度编辑抽屉后「数据源」「数据表」均为空；查看数据库 `dimension` 表，确认**根本没有数据源/数据表字段**。

### 原因分析（代码定位）

- 问题 2 实施时，维度表单的「数据源/表」定位为**弱联动辅助控件**（当时设计：维度是逻辑实体、跨表复用，不强绑表），实现为两个独立前端变量：
  - `index.vue:524-525`：`dimCascadeDsId` / `dimCascadeTable`，**不在 `dimForm` 内**，保存时只提交 `dimForm`（`saveDimHandler` :628-653），这两个值被丢弃；
  - 编辑打开（`editDimHandler` :593-596）与关闭（`onDimClose` :610-614）均调用 `resetDimCascade()` 清空 → 每次编辑必然丢失；
  - 只有 `default_column` 随表单提交入库，编辑可回显；
- 数据模型层：`dimension` 表（`metric_model.py:54-62`）只有 `dimension_name/aliases/default_column/description/oid`，073 迁移只给 `metric_definition` 加了 `source_ds_id`，未覆盖 `dimension`。

### 处置方案（已决策 ✅，用户拍板）

**镜像指标表做法：维度持久化三元组（数据源，数据表，字段名），逐表显式，不做"默认字段名"假设**（讨论共识：真实系统字段名由各建表规范决定，不存在可覆盖不可控表字段的"默认值"）：

1. **074 迁移**：`dimension` 增列 `source_ds_id BIGINT NULL`、`source_table VARCHAR(255) NULL`，并 **`default_column` 改名 `column_name`**（用户拍板采用 `column_name`；新迁移内 alter + 可回滚，历史迁移不动）；
2. 模型/CRUD：`Dimension`、`DimensionInfo` 同步改名 + 增字段，`list/create/update` 透传落库；
3. 前端：`dimCascadeDsId/dimCascadeTable` 并入 `dimForm`（键 `source_ds_id`/`source_table`）随表单提交；编辑打开时按已存值恢复级联候选（表候选 + 字段候选预加载）；`defaultDimForm` 键改 `column_name`；
4. 治理脚本：gen 草稿行内写 `source_ds_id`/`source_table`（原 `_meta` 信息提升为正式字段）、prompt 字段名改 `column_name`、apply 落库（读旧键 `default_column` 兼容既有草稿）；
5. i18n 四语言：key `dimension_default_column` 改名 `dimension_column_name`，文案「默认字段」→「字段名」；
6. 不改：检索/插桩/召回逻辑（仅字段名替换）、后端不加阻断校验（G4）。

> 注：Phase 1 召回与提示词不依赖维度落点，此改动**不改变问数行为**（开关关零差异不受影响；开关开时提示词 XML 标签 `<default_column>` → `<column_name>`）。

## 问题 6：执行详情页「匹配指标」步骤显示异常（已完成）

### 现象（A2 链路走查中发现，2026-10-13）

问数窗口执行详情页中，指标召回步骤标题显示为原始 key `chat.log.FILTER_METRICS`（其余步骤均为中文），且其下无任何内容、展开无效。

## 讨论结论 3：指标/维度跨表、跨数据源场景的处理策略

> 背景：指标、维度天然可能跨表甚至跨数据源（跨场景）。本节为架构讨论结论，**供后续 Phase 5/6 实施时遵循**，暂不产生代码改动；如需固化为规格，应回写《v201改造方案_v1.2.md》对应 Phase。

### 3.1 总原则

> **口径集中、物理分散、复杂回退**：
> 指标/维度的"含义"只定义一处（指标中心，规则 G3）；
> "跨"由执行层拆成多个**单表/单源子查询**分别执行、最后合并；
> 拆不动的**永久回退 LLM 轨道**（规则 G2）。

### 3.2 按"跨的程度"分三层

| 层次 | 例子 | 处理方式 | 依据 |
| ---- | ---- | ---- | ---- |
| 跨列（同表） | GMV = 金额 - 退款 | 无需特殊处理，`source_column`/`filter_rule` 表达 | Phase 1 已覆盖 |
| 跨表（同一数据源） | 事实表 join 维表；复合指标跨两张事实表 | LLM 轨道（现成）/ 未来受控 join（演进），见 3.3 | Phase 5 分流规则 |
| 跨数据源 | "游客量 + 酒店入住率" | **拆子查询 + 后置合并**，SQL 层永不跨源 join | `plan.sub_queries[].datasource_id`（G5：执行不在本期） |

### 3.3 同源跨表：两条路

- **路径 1（LLM 轨道，现成能力）**：复杂 join 走 LLM 直出 SQL；系统已有数据源级表关系配置 `core_datasource.table_relation`（alembic 044，edge 列表），`get_table_schema` 会把选中表的关联关系注入提示词（`apps/datasource/crud/datasource.py:577-594`），LLM 可见 join 路径，再由既有 `check_sql`/表名白名单兜底。v1.2 Phase 5 明确"多表 join → 回退 LLM"，此为**永久回退轨**。
- **路径 2（DSL 受控 join，未来演进，不进 Phase 5 首版）**：星型模型是数仓常态，纯单表 DSL 覆盖率上限偏低。演进方向：Compiler 只允许编译 `table_relation` 白名单边 + `metric_dimension_relation` 维度白名单构成的 join，用 sqlglot 拼 AST；未配置关系 → 回退 LLM。**是否立项以 Phase 0 评测集的纯单表覆盖率数据为准**（符合 G4 先观测后阻断）。⚠️ 2026-10-13 补充：评测数据仅作回归/调参的静态参考，**不作为"建不建映射/受控 join"的裁决依据**（评测无法框定开放增长的新场景，见 3.4 讨论更新 2）。

### 3.4 指标/维度数据模型如何表达"跨"

**指标**：

- 一个指标 = 一个口径锚点（`source_table` + `source_ds_id`，即问题 2 方案 A）。**指标本身不"跨"**——跨表/跨源的是它的*计算实现*。
- derived/composite 指标：经 `metric_dependency`（Phase 1 只建表）分解为子指标，每个子指标各锚一张表；未来 Calculation Planner（Phase 6 演进注记）按数据源能力选择后端：同源下推 SQL join，跨源则每子指标一条单源 SQL，Python 侧合并。
- **跨源合并发生在执行后**（Phase 6 calc_engine 已是"子查询结果合并为普通行列"的形态），不发生在 SQL 里——这是跨源不踩权限/连接限制的唯一做法。

**维度**：

- 维度是**逻辑实体**（如"游客来源地"），天然跨表跨源，物理列只是"落点"。
- **发现的欠账**：`dimension.default_column` 是单值，隐含"所有表共用一个列名"的假设；同源跨表时列名往往不同（`city`/`org_city`/`origin_city`）。Phase 5 规则"default_column 不在 metric.source_table → 回退 LLM"能兜底，但星型场景会几乎全部回退，DSL 形同虚设。
- **演进方向（Phase 5 前定即可，不急）**——把"维度→列"从单值改为带作用域的映射，两个量级：
  1. 轻量：`metric_dimension_relation` 增列 `column_override`（该指标下该维度的物理列覆盖），编译期优先用它，缺失回退 `default_column`；
  2. 彻底：独立 `dimension_column_map`（dimension_id + 表/数据源作用域 + column），复用术语库 oid/specific_ds 的作用域惯例。
- 跨源维度：同一逻辑维度在不同数据源列名/表不同，靠作用域隔离；跨源合并时按维度 key 在 Python 侧对齐（calc_engine 合并的本质是维度键 join）。

**2026-10-13 讨论更新（问题 4 附带的架构共识，修订上述欠账的处置思路）**：

1. **"默认字段名"不成立（已落地为问题 4）**：真实系统各建表规范不同，不存在可覆盖不可控表字段的"默认值"；字段对应必须 **（数据源、表、字段）逐表显式**。`default_column` 已改名 `column_name` 并与 `source_ds_id`/`source_table` 一起持久化为落点三元组（074 迁移）——但三元组仍是"维度在某一张表的落点"这**一条**记录，跨表多落点的完整映射仍属下述演进方向。
2. **不等 Phase 0 裁决"建不建映射"**：用户论点——评测集是静态快照，存量场景有限但新场景持续出现、无法被评测数据框定。故决策链从"跑评测看频率再决定"改为：**显式映射不是前置门槛，是随使用增长的缓存**——未知映射 → 回退 LLM 轨道（可运行可观察）→ 高频缺口沉淀为配置（映射是回退通道的产物，不是前提）。
3. **量级选择偏向量级 2**（`dimension_column_map`）：开放增长下配置面 = 维度数 × 实际落点数，一次录入全局复用，优于量级 1 的指标×维度格子。是否 Phase 5 落地及表结构细节到时定。
4. **沉淀机制（配套，否则配置永远为零）**：LLM 轨道日志记录"维度 → 实际选用列"的解析结果 → 治理侧发现高频未配置映射生成候选 → 人工确认入映射表（与 gen→审→apply 同一工作流）；未配置 = 回退，不报错不阻断（G2/G4 不变）。
5. **不依赖配置的硬底线**："无法枚举映射"≠"无法校验结果"——查询时**列存在性/类型校验**（表结构查询时已知）对 LLM 轨道同样适用，是开放场景下零成本的确定性保障，Phase 3 可信校验层优先做这类可判定校验。

### 3.5 权限边界（按 G5 显式声明）

- 行列级权限挂在执行侧（`datasource/crud/permission.py`），拆成单源子查询后**各源分别校验、天然复用**；
- "子查询各自合法、合并后结果集该不该可见"是新问题——**跨源结果合并的权限推断不在本期**，避免评审误判范围。

### 3.6 分阶段节奏总结

| 阶段 | 跨表/跨源策略 |
| ---- | ---- |
| Phase 1~3（当前） | 指标锚定单表 + `source_ds_id`；维度落点三元组 `source_ds_id`/`source_table`/`column_name`（074，问题 4）+ 跨表多落点靠 LLM 轨道；跨的场景靠 LLM 轨道兜底 |
| Phase 5 | 纯单表编译；多表 join 永久回退 LLM（`table_relation` 已为 LLM 供 join 路径） |
| Phase 5 之后 | 受控 join（仅 table_relation 白名单边）；维度列映射按"可累积缓存 + 缺失即回退 + 沉淀通道"设计（3.4 讨论更新 2~4），表示形式偏向 `dimension_column_map`；评测数据仅作参考不作裁决 |
| Phase 6 及未来 | 跨源 = N 个单源子查询 + calc_engine 合并；Calculation Planner 双后端 |
