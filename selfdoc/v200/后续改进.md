## 议题一：自定义提示词要不要加向量检索？

### 结论：**暂不加（维持现状）**

### 现状事实

- `custom_prompt` 表**没有 embedding 字段**。全量 DDL 检索确认，涉及该表的迁移只有：
  - `046_add_custom_prompt.py`：id/oid/type/create_time/name/prompt/specific_ds/datasource_ids
  - `069_term_custom_prompt.py`：仅新增 advanced_application
  - `070_add_table_column_comments.py:130-140`：注释清单同样无 embedding
- 全项目有 embedding 列的只有 4 张表：`terminology`(039)、`data_training`(042)、`core_table`/`core_datasource`(047)。
- 配套链路全部缺位：`common/utils/embedding_threads.py:16-48` 回填线程只注册 terminology/data_training/table/ds；术语/示例的向量召回 SQL 与阈值配置（`EMBEDDING_*_SIMILARITY/TOP_COUNT`）按表硬编码；`config.py` 无 custom_prompt 对应配置；`apps/custom_prompt` 无 save_embeddings 触发点。
- 行为参照：xpack 原版 `find_custom_prompts` **无 question 参数、按 scope 全量返回**，本来就没有检索。改造点2 属于"从 0 到 1 加检索"，复用改造点1 已验证的 `bm25_retrieve` 是成本最低、风险最小的选择。

### 不加的四条理由（按权重）

1. **当前召回瓶颈是"只按 name 打分"，不是"缺向量"**（见议题二）。
2. **改造点3 的 LLM 过滤已经补掉语义层**：链路是 `BM25 词面粗排 → LLM 语义精筛`，LLM 才是真正理解"提示词是否相关"的组件，向量召回与它信息增量高度重叠。
   - **澄清（2026-09-30 修正）**：LLM 过滤对**三类上下文统一生效**（`llm.py:486-521`，术语/SQL示例/自定义提示词在同一调用里统一编号送筛），"有 LLM 兜底"**不是** custom_prompt 独有的优势。因此本条不能反推"术语/示例也该砍向量"——区别在于：术语/示例的双路召回是 039/042 已建成的既有链路，回填线程、阈值配置等成本已沉没，且其候选中"同义词/换表述"型语义近义占比更高，向量边际增量更大；custom_prompt 是从 0 到 1 新建，需单独论证边际收益，而该收益被 LLM 精筛吃掉了大半。
3. **候选量级太小**：xpack 原版全量注入说明产品预期是管理员手工配置的少量条目。候选集 `LIMIT 2000` 等于全表；TOP-K 截断反而可能把本该全量给 LLM 看的提示词提前砍掉。
4. **成本/风险不对称**：DDL 迁移 + **xpack 双 mapper 共存下加列的高风险验证**（开源侧加列后 xpack 的 `__table__` 复用分支是否认这个列是未知数）+ 回填线程 + 维护页 4 个触发点 + 配置项，换取小量级下略微提升的词面召回。

### 启动条件（满足任一再重新评估）

| 触发条件 | 说明 |
|---|---|
| 提示词量级上百，且 name 命名高度专业化、与用户提问用词差异大 | BM25 词面交集失效 → 召回为空或过少；LLM 过滤只能精筛**已召回**的候选，找不回没进候选的条目（且总数不足 `MIN_CANDIDATES=3` 时整个过滤会被跳过，见 `llm.py:492-494`） |
| 线上出现"该匹配却没匹配"的反馈，复盘显示漏的是语义近义而非词面缺失 | 有实证再动 |
| `LLM_CONTEXT_FILTER_ENABLED=False` 成常态 | 失去语义兜底，粗排质量权重上升 |

### 若将来要做的步骤（供参考，未实施）

1. alembic 迁移：`custom_prompt` 加 `embedding VECTOR`（参照 039）+ 070 风格中文注释
2. 模型 `CustomPrompt` 加字段（**高风险点**：xpack 双 mapper 共存，需先验证 `__table__` 复用分支能否安全挂新列）
3. curd 加 `save_embeddings`/`run_fill_empty_embeddings` + `embedding_threads` 注册 + `main.py` 启动补向量
4. `find_custom_prompts` 加向量召回分支、与 BM25 结果合并去重（照抄术语/示例双路合并结构）
5. `config.py` 加 `EMBEDDING_CUSTOM_PROMPT_SIMILARITY/TOP_COUNT`；维护页 4 个变更点（create/update/delete/批量导入 upload_excel）触发回填
6. 改造点3 候选集自然扩大，`llm_filter_context` 无需改

### 最优先的观察动作（不涉及向量）

先跑真实问题看 `find_custom_prompts` 的召回条数与 LLM 过滤的 drop 率。若召回常年 0 条（`MIN_SCORE=0.0` 严格大于，零分词交集即空），要调的是**阈值与打分字段**，依然轮不到向量。

## 议题二：BM25 打分要不要纳入 prompt 正文？

### 结论：**维持 name-only**

### 关键澄清：长度限制不适用于 BM25

- **BM25 无输入长度限制**，处理几万字 prompt 无压力，不需要截断或约束用户长度。长度唯一影响是 Okapi 公式 `b=0.75` 的长度归一化——文档越长单次命中分越薄，这反而是**防长 prompt 靠通用词刷分**的天然保护。
- **长度限制只对 embedding 成立**（text2vec 类模型 max_seq_length 通常 256/512 token）。"prompt 正文不可限长"这个理由**支持的是'不做向量'，不构成'BM25 也不看 prompt'的论据**，两个决策应分开。

### skill 类比的成立前提

参考 claw 系统的 skill 选择逻辑：skill 靠 metadata description（为"被选中"而写的场景/触发条件/边界说明）被选中；本项目把 `custom_prompt.name` 视作同物（适用场景、功能说明）。类比逻辑自洽，但差异在约束强度：

| | skill description | `custom_prompt.name` |
|---|---|---|
| 定位 | 元数据/说明书 | 表面上是"名称" |
| 长度 | 几十~几百字 | `VARCHAR(255)`，通常几个字 |
| 录入引导 | 模板强制写场景 | 无引导 |

**类比成立与否取决于 name 实际写成什么。** 当前是本人使用、清楚 name 的功能设定，故成立。

### prompt 参与 BM25 的真实代价：噪声，不是长度

- prompt 自由文本通用词（"查询""数据""请"）密度高，几乎与任何问题有分词交集 → `MIN_SCORE=0.0`（严格大于）形同虚设，召回退化为"全量过 TOP_K"；
- 仅 prompt 弱命中、name 毫无关系的条目挤占 TOP_K 名额；
- 这些条目最终大概率被改造点3 的 LLM 过滤 drop 掉——花了召回预算，产出为零。

这也解释了问题3 当初从 `name+prompt` 收敛到 `name` 的合理性：**末端已有 LLM 语义过滤的链路里，粗排的角色是"高精度地别漏掉该来的"，不是"尽可能多捞"**；各司其职不重复（LLM 过滤能看到完整 prompt 正文）。

### 若将来出现漏召回的排查顺序

1. name 是否写得太短太泛 →（此时正确动作是**改录入规范**：把"name = 适用场景/功能说明"显式化，等价于 skill 体系里"description 怎么写"那一环）
2. `KEYWORD_RETRIEVAL_MIN_SCORE` 是否过严
3. 最后才考虑 prompt 加权参与（name 高权、prompt 截断低权的双字段打分）

## 议题三：LLM 过滤层给大模型看什么内容？

### 当前实现（`backend/apps/chat/task/llm.py:500-521`）

| 类别 | 当前喂给 LLM 的内容 |
|---|---|
| 术语 | `{words}：{desc[:500]}` —— 词+描述双字段 |
| SQL示例 | `问题：{q[:200]}；示例SQL：{a[:500]}` —— **问题和 SQL 都放** |
| 自定义提示词 | `{text[:500]}` —— **只有 prompt 正文，没有 name** |

> 注：`prompt_candidates` 来自 `find_custom_prompts` 返回的 `prompt_list`（**纯正文字符串列表**，见 llm.py:445-450）。

### 结论

| 类别 | 建议 | 理由 |
|---|---|---|
| 术语 | **不动** | 词+描述结构已合理 |
| SQL示例 | **不动，保留 SQL** | 过滤的判断目标是"SQL 有没有参考价值"，只有 SQL 本体能回答 |
| 自定义提示词 | **补上 name**，改为 `{name}：{prompt[:500]}` | 消除信息错配（见下） |

#### 自定义提示词：为什么现状是错配

- 粗排（BM25）**按 name 打分**选出这批候选，精排（LLM）却**看不到 name**——LLM 无法复核"这条凭什么进来"，也丢掉了设定好的"适用场景"信号。
- 只放 name 也不行：name 是短标签，LLM 缺规则实质，判断退化成猜。
- 正确形态与术语对齐的双字段：**name = 快速信号（场景标签），正文 = 确认信号（规则本体，决定这条规则会不会作用于当前查询）**。成本增量可忽略。

**实现约束（未实施，标风险）**：`prompt_list` 同时被 `end_log(full_message=prompt_list)` 用于日志、前端 `LogCustomPrompt.vue` 按纯文本 `v-dompurify-html` 渲染。要给 LLM 加 name，必须**另存一份结构化暂存**（或改 `find_custom_prompts` 返回结构），**不能直接改 `prompt_list` 元素类型**，否则破坏日志渲染契约。

#### SQL示例：为什么 skill 类比在这里不成立

skill 选择回答的是"这个 skill 是干什么的"（看 description 即可）；SQL 示例过滤回答的是"**这条示例的 SQL 对当前问题的生成有没有参考价值**"——只有 SQL 本体能回答。只看 question 会两头误判：

1. **question 相似 ≠ SQL 可参考**：两条都问"GDP"，一条年度总量、一条同比增速，question 高度相似但只有一条有用 → 双双被保留。
2. **question 措辞不同 ≠ SQL 不可参考**：question 是手工维护的主观标签、措辞随意；SQL 是客观事实 → 套路同构的示例可能被误删。

成本上 `[:500]` 截断 + TOP 数量有限（BM25 TOP 10 / 向量 TOP 5），token 已可控，没有砍 SQL 的紧迫性。

**什么情况下才该削减 SQL**：示例量级大到过滤 prompt 明显超预算，或 question 字段已规范化为完整场景描述。届时折中也**不是砍掉 SQL 而是压缩 SQL**（截断调短至 200 左右，或只留 FROM/聚合骨架）——保留客观信号、只降 token。

#### 统一范式

三类上下文对齐到同一形态：**"元数据/标题（是什么）+ 实质内容（干什么）都给 LLM"**，让精排同时掌握场景信号与实质信号。真正需要调整的只有自定义提示词一类。
