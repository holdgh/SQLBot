# SQLBot 企业级问数改造方案（v201 分步实施版）

> 来源：基于《gpt关于sqlbot的改造建议.md》全部讨论（含"澄清改造细节""指标数据存储"两轮追问），
> 结合本代码库实际实现盘点后收敛的**最终可分步执行方案**。
>
> 核心目标：将 SQLBot 从「RAG 增强型 Text2SQL」升级为「**Metric + DSL 驱动的企业级查询系统**」，
> 且**每个阶段完成后系统直接可运行**，后续阶段逐步叠加。

---

## 一、现状盘点（代码事实，方案的立足点）

| 能力 | 现状 | 关键位置 |
| ---- | ---- | ---- |
| 术语/SQL示例/自定义提示词检索 | BM25 + pgvector 混合召回 + LLM 二次过滤（已具备，可直接复用） | `terminology/curd/terminology.py:845`、`data_training/curd/data_training.py:524`、`custom_prompt/curd/custom_prompt.py:404`、`chat/task/llm.py:498 llm_filter_context` |
| Schema 注入 | 按数据源取表 → DDL 拼接 → 可选向量选表（**已有 schema 检索雏形**） | `datasource/crud/datasource.py:519 get_table_schema`、`:569 calc_table_embedding` |
| SQL 安全校验 | sqlglot 只读/危险函数校验 + 表名白名单（**已有**，缺业务口径校验） | `db/db.py:1072 check_sql_read`、`llm.py:1547 check_sql`、`llm.py:1556-1562` |
| 权限 | 接口级 + 行列级权限（**已有**） | `datasource/crud/permission.py`、`llm.py:1110/1160` |
| 主链路 | 单体编排函数 `run_task`：filter→选ds→generate_sql→check_sql→execute→chart | `chat/task/llm.py:1448` |
| 指标中心 / DSL 中间层 / 计算引擎 | **完全缺失** | — |
| 工程惯例 | `【改造标记 XXX】` 增量改造、旧代码注释保留、config 开关、alembic 只增不改 | 如 `RAG-KEYWORD`、`LLM-CONTEXT-FILTER`、`CUSTOM-PROMPT` |

**结论**：RAG 底座、安全校验、权限都不需要重造；真正要新建的是
**指标中心、Query Plan（含计算意图）、SQL Builder、计算引擎**，外加 **Schema 语义文档**的治理增强。

## 二、目标链路（改造后）

```text
                  用户问题
                     |
                     ↓
        ┌── Query Understanding（Phase 3）──┐
        │  意图/实体/计算意图识别             │
        └──────────────┬───────────────────┘
                       ↓
              Query Plan (JSON)  ←—— pydantic 严格校验
                       |
      ┌────────────────┼─────────────────┐
      ↓ (指标命中,短路)  ↓ (兜底)           ↓
 指标RAG(Phase 1)   术语RAG(保留)      Schema语义文档RAG(Phase 6)
      |                |                    |
      └────────────────┴────────────────────┘
                       ↓
          DSL / SQL Builder 确定性编译（Phase 4）
                       |
        ┌──────────────┴──────────────┐
        ↓ DSL轨道成功                   ↓ 任一环节失败
   业务规则校验(Phase 2)  ←——————→  原 LLM 直出 SQL（保留兜底）
        ↓
   既有 check_sql / 表白名单 / 权限 / 执行（不动）
        ↓
   计算引擎（Phase 5，按 plan.calculation 程序化计算）
        ↓
   既有图表生成 / 前端展示（契约不变）
```

**每个 Phase 只在链路上"插桩"，不重写既有环节；DSL 轨道全程可回退到原 LLM 轨道。**

## 三、兼容性总则（每个步骤都必须满足）

1. **配置开关**：每个 Phase 在 `backend/common/core/config.py` 新增独立开关，**默认关闭 = 行为与当前完全一致**；开关打开才启用新能力。
2. **回退链**：DSL 轨道中"plan 生成 → schema 校验 → 编译 → 规则校验"任一步失败，自动回退原 `generate_sql` LLM 直出流程，问数不中断。
3. **数据库只增不改**：alembic 迁移只新建表，不修改/删除既有表和列；迁移可独立回滚。
4. **旧代码注释保留**：沿用项目 `【改造标记 XXX】` 惯例，替换段旧代码注释保留、禁止删除。
5. **前端契约不变**：SSE 消息类型（`sql`/`sql-data`/`chart`/`finish`）与结果表结构不变；计算引擎结果合并为普通行列结构后再进入图表生成。
6. **新模块独立**：新建 `backend/apps/metric/` 等 app，路由在 `apps/api.py` 中注册，与现有路由无路径冲突；指标库为空时检索返回空，等价于未启用。

## 四、分步实施路线（按优先级排列）

### Phase 0：评测基线（前置，不改产品代码）

| 项 | 内容 |
| -- | -- |
| **目标** | 在任何改造前量化当前链路准确率，作为后续每步的验收标尺。没有基线，无法证明改造收益。 |
| **改动** | 新建评测集（建议 `tests/evals/cases.jsonl`：`{question, 断言类型, expected}`，覆盖：单指标取数、过滤、时间、排名、同比、多表关联、模糊业务词）；新建评测脚本，走现有 API/`LLMService` 跑批，输出 SQL 正确率/结果正确率。 |
| **兼容性** | 不触碰任何产品代码。 |
| **验收** | 能一键跑出基线报告（如 80 条问题的准确率），结果落盘可复查。 |
| **工作量** | 2~3 天。 |

### Phase 1：指标中心 MVP（★★★★★，最高优先级）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**查什么**"——业务口径的权威来源。Schema 只能告诉模型"库里有什么"，指标中心回答"业务上该用哪个字段、怎么算"。 |
| **数据模型** | 新建 3 张表（alembic `072_metric_center`，只增表）：<br>`metric_definition`（metric_name/description/business_domain/source_table/source_column/aggregation/filter_rule/time_field/status/version）<br>`metric_alias`（metric_id/alias，关键词召回用）<br>`metric_document`（metric_id/document_text/embedding vector/keyword_list 预留、可整表重建）。<br>**元数据（Source of Truth）与检索索引分离**：口径变更→重算 document，不动业务元数据。 |
| **模块** | 新建 `backend/apps/metric/`（models/curd/api 三件套，**结构照抄 `terminology` 模块**）；路由注册于 `apps/api.py`（沿用 CUSTOM-PROMPT 的注册惯例）；前端新增指标管理页面（参照术语管理，独立页面，不影响问数页）。 |
| **检索** | 复用现有设施：BM25（`common/utils/keyword_retrieval.py`）+ pgvector 向量召回 + 并入 `llm_filter_context`（`llm.py:498`）做 LLM rerank。**不新建检索引擎**。`keyword_list` 列先预留不物化（指标量级几百~几千，运行时分词足够）。 |
| **接入点** | 仿照三路 filter：在 `run_task`（`llm.py:1458-1465`）与无数据源分支（`llm.py:994`）新增 `filter_metric_template`，候选项暂存并进 `llm_filter_context`；在 `init_messages` 组装提示词处注入"相关业务指标"块（与术语并列，**指标块排在术语块之前**）。 |
| **元数据治理** | 提供一次性辅助脚本：LLM 根据 DDL + 数据源注释 + 样本数据生成表/字段业务描述与指标候选，人工确认后入库。这是本 Phase 的真正工作量大头（加工层质量取决于内容，不是格式）。 |
| **兼容性** | 开关 `METRIC_CENTER_ENABLED`（默认 False）；False 时 filter 不执行、提示词无变化；指标库为空时召回为空，同样无变化。SQL 生成仍走原 LLM 流程，**本 Phase 不碰 SQL 生成**。 |
| **验收** | 开关关=回归通过（与 Phase 0 基线无差异）；开关开=含"游客量/客流/接待人数"等业务词的问题，提示词中出现正确指标定义，评测准确率不下降（目标提升）。 |
| **工作量** | 后端 1~2 周（含治理脚本与首批指标录入）。 |

---

### Phase 2：指标口径校验（业务规则 Validator，★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**SQL 正确 ≠ 数据正确**"。把业务规则从 Prompt（非强约束）下沉为程序校验。**对 LLM 直出 SQL 轨道同样生效，不依赖 DSL**，因此可尽早独立上线。 |
| **改动** | ① `metric_definition` 增补/关联 `metric_rule`（rule_type：必须过滤/禁止字段/强制聚合，rule_content）；② 新建 `backend/common/utils/metric_validator.py`：基于 sqlglot AST 检查生成 SQL 是否违反命中指标的规则（如"游客量必须 `status=1`""收入禁止直接 sum"）；③ 挂接点：`llm.py:1547 check_sql` 之后、执行之前。 |
| **兼容性** | 开关 `METRIC_RULE_ENFORCE`：**默认 False = 仅记录告警日志（不阻断）**，True = 违规拒绝并回退/报错。规则为空 = 不校验。 |
| **验收** | 构造缺 `status=1` 的 SQL，告警模式有日志、执行不受影响；强制模式阻断且前端收到可读错误；无规则指标零影响。 |
| **工作量** | 3~5 天。 |

### Phase 3：Query Plan 语义解析层（★★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**LLM 一次性任务过重**"与"**计算意图放哪**"：先结构化理解，再生成。计算意图是 Query Plan 字段、不是指标属性——**本 Phase 的 plan schema 必须一次设计到位（含计算意图与多子查询结构），执行可后置到 Phase 5**。 |
| **Plan 结构** | 新建 `backend/apps/chat/schemas/query_plan.py`（pydantic）：<br>`{query_type, metrics[], dimensions[], filters[], time_range{current,previous}, calculation{type, expr}, sub_queries[]}`。<br>**关键设计**：`calculation.type`（yoy/qoq/share/growth/rank/none）决定子查询拓扑——同比展开为两个 time_range 子查询 + 比值表达式。这是后续计算引擎的协议，也是文旅规划 Agent DAG 的退化形式。 |
| **生成** | 新增 `generate_query_plan`：LLM 输出 JSON → pydantic 严格校验 →（可选）校验通过的 plan 注入指标/schema 上下文再编译。**本 Phase 默认只生成 + 校验 + 落日志/前端展示，不改变 SQL 生成路径**，先验证"理解"准确率。 |
| **挂接点** | `llm.py` 中 `generate_sql`（`:1509`）之前插桩；plan 生成失败/校验失败 → 走原逻辑，零影响。 |
| **兼容性** | 开关 `QUERY_PLAN_ENABLED`（默认 False）。False = 不调用 plan 生成，零额外 LLM 开销。 |
| **验收** | 开关开：评测集中"同比/环比/排名/趋势"类问题的 plan 解析正确率 ≥ 目标值（如 85%）；**最终 SQL 与结果与 Phase 0 基线完全一致**（本 Phase 不改 SQL 路径）。 |
| **工作量** | 1 周（schema 设计 + 提示词 + 校验 + 落日志）。 |

---

### Phase 4：SQL Builder（DSL → SQL 确定性编译，★★★★★）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**怎么查**"：从"让 LLM 猜 SQL"变为"系统编译 SQL"。 |
| **改动** | 新建 `backend/apps/chat/task/sql_builder.py`：<br>① **解析**：plan.metric → `metric_definition` 得 table/column/aggregation/filter_rule/time_field；dimension/filter → 字段映射（未命中维度时**编译失败→回退**）；<br>② **编译**：基于 **sqlglot AST**（项目已依赖，复用 `extract_tables_from_sql` 等既有工具）组装 SELECT/WHERE/GROUP BY/时间条件/指标默认过滤，**禁止字符串拼接 SQL**；<br>③ **单表聚合主干优先**：DSL 覆盖"指标+维度+过滤+时间+分析类型"；多表 join、窗口函数等复杂查询**不进 DSL 轨道**，直接走原 LLM 轨道（双轨制，避免通用编译器的无底洞）。 |
| **挂接点** | `QUERY_PLAN_ENABLED` 且 `DSL_COMPILE_ENABLED` 同时开启时：`generate_query_plan` → `sql_builder.compile` 成功 → 产出的 SQL **送入既有 `check_sql`（`:1547`）起的原流程**（表白名单、权限、执行、图表全部复用，一行不改）；失败 → 原 `generate_sql`。 |
| **兼容性** | 双开关默认 False；回退链完整；编译产物与 LLM 产物走同一校验执行管线，权限逻辑（`generate_filter`）无差别生效。 |
| **验收** | 评测集按题型分桶：单指标/带过滤/带时间/排名类问题走 DSL 轨道（日志可见），结果正确率 ≥ LLM 轨道；复杂关联题全部正确回退；整体准确率不低于 Phase 0 基线。 |
| **工作量** | 1.5~2 周（解析 + 编译 + 回退 + 单测）。 |

---

### Phase 5：计算引擎（★★★★，与 Phase 3 结构配套、实现后置）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**怎么算**"：同比/环比/占比/增长率由程序计算，LLM 只做表达，消灭 `(current-last)/last` 与 `current/last` 混用。 |
| **改动** | 新建 `backend/apps/chat/task/calc_engine.py`：输入 `plan.calculation` + 各子查询结果，输出合并结果表。**实现约定**：<br>① SQL Builder 按 plan 展开为 N 个子查询（同比=2 个时间窗），分别执行；<br>② 计算函数库：`yoy/qoq/share/growth/rank/...`（纯 Python，除零保护、精度约定）；<br>③ **输出合并为普通行列结构**（如 `period | value` 或 `current | previous | growth`），使下游 `save_sql_data`、图表生成、前端 SSE 契约**完全不变**。 |
| **挂接点** | `llm.py` `execute_sql`（`:1619`）附近，plan.calculation 非 none 时启用；无 plan / calculation=none 走原单 SQL 执行。 |
| **兼容性** | 开关 `CALC_ENGINE_ENABLED`（默认 False）。LLM 轨道（无 plan）永不触发本引擎。 |
| **验收** | "同比增长多少"类问题：结果由代码算出（日志含计算过程），与人工核算一致；除零、空结果有确定性处理；图表正常渲染。 |
| **工作量** | 1 周。 |

---

### Phase 6：Schema 语义文档检索增强（★★★，可与 Phase 3~5 并行）

| 项 | 内容 |
| -- | -- |
| **目标** | 解决"**去哪查**"的规模化问题，并补齐元数据"内容"短板。**注意：检索能力已有（`TABLE_EMBEDDING_ENABLED`），本 Phase 的实质是内容治理 + 文档化。** |
| **改动** | ① 新建 `table_metadata` / `column_metadata` / `schema_document`（object_type/object_id/document_text/embedding），元数据与检索索引分离，同 Phase 1 模式；<br>② **语义文档加工层**：把"DDL/JSON 原样 embedding"替换为"业务语义文本 embedding"（表用途、字段中文含义、支持的分析），避免 `varchar/bigint/id` 技术噪声；文档由 Phase 1 的治理脚本顺带生成；<br>③ 复用 `datasource.py:569 calc_table_embedding` 的向量选表框架，仅替换 embedding 文本来源；<br>④ **指标短路**：DSL 轨道命中指标时，直接用 `metric_definition.source_table` 取表结构（现成 `get_table_schema(..., embedding=False, table_list=[...])` 用法），**跳过向量检索**——指标优先、schema 兜底，是串行关系而非并行两路。 |
| **同步** | 指标侧：保存事件即重建 document；schema 侧：挂接数据源元数据同步任务（参考既有 `table_embedding.py:43` 的批量计算）。 |
| **兼容性** | 开关 `SCHEMA_DOC_ENABLED`（默认 False = 走现有 DDL embedding 路径）；两路径互为回退。 |
| **验收** | 同一问题在两条路径下选表一致或新路径更优；评测"来源分析/趋势/排名"类选表准确率提升；表结构变更后文档能重建。 |
| **工作量** | 1~1.5 周（含治理）。 |

### Phase 7：DSL Example 迁移 + 全量回归 + 灰度切换（收尾）

| 项 | 内容 |
| -- | -- |
| **目标** | 用评测数据驱动切换决策，完成从"可选能力"到"默认轨道"的过渡。 |
| **改动** | ① SQL 示例库（data_training）逐步沉淀为 **DSL Example**（问题模式 → plan 模板），提示词中 DSL 轨道示例优先、SQL 示例保留兜底；② 全量跑 Phase 0 评测集，**按题型对比 LLM 轨道 vs DSL 轨道**；③ 分级放量：`DSL_COMPILE_ENABLED` → 按数据源/助手灰度 → 默认 True（LLM 轨道永久保留为回退）；④ 复盘 Prompt 定位：业务规则已下沉到指标中心/Validator，自定义提示词回归"表达偏好"，避免规则双写。 |
| **兼容性** | 灰度全程可一键回退（开关粒度到数据源）。 |
| **验收** | DSL 轨道整体准确率 ≥ LLM 轨道且复杂题回退无损；连续运行无新增异常日志。 |
| **工作量** | 1 周 + 持续运营。 |

## 五、优先级与依赖总表

| 序 | Phase | 解决问题 | 优先级 | 依赖 | 开关（默认关） | 完成即可运行 |

| 0 | 评测基线 | 度量 | ★★★★★ | 无 | 无（不改代码） | ✅ |

| 3 | Query Plan | 理解+计算意图 | ★★★★★ | 1 | `QUERY_PLAN_ENABLED` | ✅（不改 SQL 路径） |
| 4 | SQL Builder | 怎么查 | ★★★★★ | 1+3 | `DSL_COMPILE_ENABLED` | ✅（双轨回退） |
| 5 | 计算引擎 | 怎么算 | ★★★★ | 3（结构） | `CALC_ENGINE_ENABLED` | ✅ |
| 6 | Schema 语义文档 | 去哪查（规模） | ★★★ | 可并行（1 的治理成果复用） | `SCHEMA_DOC_ENABLED` | ✅ |

**依赖要点**：

- Phase 6 与 Phase 3~5 无代码依赖，元数据治理可复用 Phase 1 脚本，表规模大/注释缺失严重时可提前并行。

## 六、风险与缓解

| 风险 | 缓解 |
| ---- | ---- |
| DSL 通用化无底洞（join/窗口/多表） | 双轨制：DSL 只覆盖单表聚合主干，复杂查询永久走 LLM 轨道 + Validator 兜底；按评测命中率逐步扩 DSL 表达能力 |
| 指标中心录入成本高、没人维护 | 治理脚本 LLM 半自动生成 + 人工确认；先核心指标（Top 30 高频问题覆盖）再铺开；指标与看板/问答命中率挂钩运营 |
| 提示词与指标中心规则双写冲突 | Phase 7 明确：规则类内容只进指标中心/Validator，自定义提示词仅保留表达偏好 |
| 多开关组合爆炸 | 开关按 Phase 独立、文档化默认值；灰度期只开组合矩阵（全关/plan only/plan+compile）三种 |
| 计算结果破坏前端契约 | 计算引擎输出统一为行列结果表，复用 `save_sql_data` 与图表生成，SSE 消息类型不新增 |
| 指标口径变更的历史数据 | `metric_definition` 预留 `version`/`status`，问答记录落 plan 快照，可追溯当时口径 |

---

## 七、一句话总结

> 按 **评测基线 → 指标中心 → 口径校验 → Query Plan → SQL Builder → 计算引擎 → Schema 语义文档 → 灰度切换**
> 八步推进；每步独立开关、只增表不改链、DSL 轨道全程可回退 LLM 轨道，
> 最终把 SQLBot 从「RAG 增强 Text2SQL」升级为「**Metric + DSL 驱动的可信问数系统**」。
