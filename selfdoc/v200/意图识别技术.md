# 意图识别新技术（面向Agent/BI问数系统，工业落地视角）
传统方案：BERT微调分类器、关键词规则，**固定标签、依赖大量标注、新增意图要重训**。新范式核心转变：从「静态标签分类」升级为**上下文推理+检索增强+多目标结构化输出**，适配你做的SQLBot、问数、Agent工具调用场景。

## 1. RAG增强意图识别（REIC / Intent-RAG，落地最广）
核心：**向量库存储意图定义、标准问法、历史badcase，推理前先召回相似样例，再送入LLM做意图判定**
- 解决痛点：标签空间巨大（几百个意图，比如BI问数里几十种查询、过滤、对比、导出意图），全部塞进Prompt会超长；新增意图不用重新微调模型，只更新向量库。
- 流程：用户query → Embedding召回TopK相似意图样例/标签定义 → 把召回片段放进prompt → LLM输出结构化意图+置信度。
- 适配场景：你的问数系统，区分【查询指标、筛选维度、同比环比、导出报表、修改SQL、澄清询问】等细粒度意图。

## 2. 结构化输出 + 函数调用式意图识别（生产主流）
不再让模型输出自由文本，强制输出固定JSON/Pydantic枚举结构，直接绑定工具调用：
```json
{"intent":"metric_query","confidence":0.92,"slots":{"metric":"销售额","dim":"地区"}}
```
- 特点：**格式强约束，规避解析失败；意图识别和槽位抽取一次性完成**，零额外解析开销；支持零样本/少样本。
- 工程优化：置信度阈值分流，低置信度走澄清追问，避免误判。
> 对应你之前写的prompt约束：生成SQL时严格对齐schema，这套结构化输出可以把表名、字段约束一并带进意图输出。

## 3. 分层/漏斗式意图混合架构（工业生产标准方案）
不是单一模型，多级分流，兼顾延迟、成本、准确率：
1. **规则层**：高频固定query（如“导出报表”），正则/关键词，0ms，拦截30%~40%流量；
2. **轻量Embedding向量检索层**：BGE/Sentence-BERT，语义匹配标准问法，10~50ms，处理同义改写；
3. **小模型微调层（SetFit/轻量encoder）**：少量样本即可训练，处理中等难度歧义；
4. **LLM大模型层**：仅兜底模糊、多意图、跨上下文复杂query，占比控制在5%以内。

## 4. 少样本/零样本意图发现（IntentGPT、L-ZCAM）
- 零样本：直接给意图标签定义，不需要标注样本；
- 少样本In-Context Learning：每个意图给2~5条样例，不用梯度更新；
- 无监督意图发现（Auto-Intent）：从历史对话轨迹自动挖掘新意图，**自动扩充标签体系**，适合业务持续迭代，不需要人工标注新意图。
> 优势：私有化项目快速冷启动，客户业务变更，新增查询意图不用大规模标注。

## 5. 神经符号 + 本体增强意图（NOEM³A）
把**业务本体/知识图谱、意图层级关系**注入模型，符号规则+神经网络融合。
- 例如BI领域本体：指标、维度、数据表之间的关系；模型识别意图时，会校验“该指标是否支持按该维度查询”，过滤非法意图，降低幻觉。
- 适合低资源端侧、私有化部署，小模型也能获得强约束能力，适合问数系统的表/字段合法性校验。

## 6. 流式意图检测（IntentFlow / PASK）
边输入边实时识别意图，不等用户说完完整句子，**增量推理**。
- 面向语音、实时对话Agent；支持预判用户需求，提前触发工具预加载；
- 配套长期记忆模块：结合历史会话、用户历史偏好做个性化意图推断（IntPro检索式上下文意图），多轮对话下意图不会断，适合连续多轮问数场景，比如：
> 用户：帮我看2025销售额 → 接着说：按省份拆分，再对比去年同期
> 模型需要结合上文，识别复合意图，而不是孤立看单句。

## 7. 多模态意图识别（TMIR / IntentVLM）
文本+语音+图片/视频联合识别意图，评估每个模态可信度再融合；
> 你的BI场景暂时用不到，多用于机器人、客服带截图对话场景。

## 8. 多意图拆解与意图因果推理
用户一句话包含多个意图（复合意图）：`查询本月营收，并且生成图表导出`。
新技术不再输出单一标签，而是**拆解为意图子任务序列**，和Agent任务规划打通，直接映射到工具调用链（查询→绘图→导出）。

# 对比传统BERT方案（一句话总结差异）
- 传统：分类任务，固定标签，大量标注，输出单一标签，**和下游工具/SQL解耦**；
- 新方案：推理任务，动态标签，少标注，结构化输出，**意图识别直接和工具、SQL生成链路打通**，优先解决开放域、长尾、业务迭代场景。

# 针对你的【问数/SQLBot项目】选型建议
1. 主架构：**四层漏斗 + RAG意图检索 + 结构化JSON输出**；
2. 向量库存放：意图定义、标准问法、历史错误case、schema表字段描述；
3. 置信度兜底：低于阈值触发澄清（“你是想查询销售额还是订单量？”）；
4. 神经符号校验：识别意图后，增加一层本体校验，判断指标、维度、表字段是否合法，减少生成无效SQL。

## 一、专门做意图NLU平台（原生面向意图识别、槽位填充，开箱API，私有化可选）
1. **百度智能云 UNIT**
国内老牌NLU平台，原生意图+槽位抽取，支持自定义意图标签，可配置**不返回思考文本，只输出结构化JSON**；支持少量样本、规则+大模型混合，私有化部署。适合BI问数的指标、维度槽位抽取。
2. **阿里云 Model Studio NLU意图识别**
专门的意图API，可定义意图枚举、槽位schema，返回固定结构，无多余文字；支持MaaS调用、私有化。
3. **Azure CLU（微软对话语言理解）**
工业级NLU，只输出意图名称、置信度、槽位，无思考文本；支持多轮上下文意图，海外项目常用。
4. **Picovoice Rhino**
端侧专用意图识别，纯结构化输出，完全没有大模型思考文字，低延迟，适合固定领域命令式意图。
5. **Botpress**
对话平台内置NLU引擎，可配置意图、槽位，API返回纯JSON，可私有化部署。

## 二、结构化输出SDK库（工程最常用，接管LLM调用，强制只输出JSON，剔除思考内容，适配SQLBot）
> 不是模型，是封装层，在token生成阶段或者调用层强制约束，**禁止模型输出思考文字**
1. **Instructor（Python，最流行）**
封装OpenAI/GLM/Qwen/Claude等客户端，直接传入Pydantic模型，自动重试校验，**返回强类型对象，不会附带思考文本**；你定义`intent,confidence,slots`结构，直接用于BI意图识别。
2. **Outlines（约束解码，工业硬核）**
token级约束解码，编译JSON Schema为有限状态机，**模型在生成时就不能输出非法token，根本无法输出思考文字**，本地私有化模型（vLLM/Ollama）首选。适合高稳定性要求的问数系统，杜绝“先思考再输出json”。
3. **Guardrails AI**
结构化校验框架，拦截自然语言解释文本，强制输出schema，校验失败自动重试。
4. **Vercel AI SDK（TS）**
`generateObject`，传入Zod schema，原生结构化输出，不返回思考内容，适合前端+Node服务。

## 三、大模型厂商原生结构化输出API（模型原生支持strict schema，关闭思考）
> 就是前面提到GLM、Qwen这类，原生支持`response_format`，开启严格模式后，**只输出JSON，不会输出前置思考文字**
- 智谱GLM：`response_format`+strict模式，Function Calling，纯JSON输出
- 通义Qwen：原生结构化输出，支持json_schema强约束
- OpenAI GPT系列：`json_schema` strict=true，强制无思考文本
- Claude：Tool Use，强制返回tool入参JSON，不输出自然语言思考

## 四、专门面向Agent/决策意图的专用模型（JEV / U2-Decision）
1. **JEV（意图决策模型）**
专门做意图分类、工具路由，**原生只输出结构化决策JSON，没有CoT思考**，不需要prompt强约束，适合大量意图分类场景，BI、客服Agent大量使用。
2. **云知声 U2-Decision**
决策专用模型，做意图路由、任务判定，输出结构化决策，无多余自然语言。

# Jev（TypeSafe AI）完整说明，正好对应你要的：**无思考内容，直接结构化决策输出**
Jev（你听到的就是它，之前简写JEV），TypeSafe AI 2026年9月发布的 **System One 决策模型**，创始人是前OpenAI研究员、GPT系列核心作者Diogo Almeida。
核心定位：**不生成自然语言、没有CoT思考过程，只输出带置信度的结构化决策结果**，业内戏称“哑巴AI”，专门做意图分类、工具路由、分支判断，完美匹配BI问数系统的意图识别场景。

## 核心原理（和普通LLM本质差异）
普通LLM：先输出思考文本，再输出JSON；哪怕开`strict json_schema`，底层依然是文本生成。
Jev：**原生就不是文本生成模型**。
输入分为两块：
1. `state`：用户query、会话上下文、业务schema（你的指标/维度/表信息）
2. `questions`：预先定义好的候选选项（意图枚举：metric_query、export_report、sql_modify、clarify等）

输出固定结构化结果：
- choice：选中的意图标签
- score：置信度0~1
- noul：命题真假概率（可选）
> 全程**不存在任何思考文本、解释文字**，直接返回可被代码读取的决策结构，延迟很低（约70ms）。

## 在SQLBot/问数系统的落地用法
1. 预先定义全部意图枚举集合：指标查询、同比对比、导出报表、修改SQL、澄清询问、拒绝回答等；
2. 用户query + 上下文送入Jev，传入候选意图列表；
3. Jev直接返回`{intent:xxx, confidence:xxx}`；
4. 后端阈值分流：置信度≥0.85 → 进入SQL生成；低于阈值 → 触发澄清追问。

### 优势（对你场景）
✅ 完全消除“模型夹带思考文字”问题，不需要额外做JSON校验/清洗；
✅ 轻量、低延迟，适合高并发意图路由；
✅ 标签改动仅需要更新候选选项，**不需要重新微调模型**，冷启动快；
✅ 天然适合多意图判定、歧义判断。

### 局限（重点，私有化项目要评估）
❌ 当前仅开放API内测，**无开源权重，无法本地私有化部署**；
❌ 擅长**分类/多选决策**，槽位抽取能力弱；如果除了意图，还需要同时提取指标、时间、维度槽位，Jev只能完成意图判定，槽位抽取仍要搭配其他模型；
❌ 国内网络访问有门槛，数据出境合规风险，**国企/运营商项目受限**；
❌ 只能做限定候选集内的选择，不适合开放域、不在候选列表内的未知意图挖掘。

## 对比选型小结（针对你的BI问数项目）
- 如果是**云上项目、不考虑私有化**：Jev非常适合做意图路由，专门负责判定用户属于哪一类意图，无CoT，延迟低。
- 如果**私有化部署、数据不能出境**：Jev无法选用，备选方案：Outlines约束解码 + GLM/Qwen。

## 补充：和云知声U2-Decision区别
- Jev：海外TypeSafe，侧重通用软件决策、Agent意图路由；**没有文本生成能力**
- U2-Decision：国内厂商，面向语音NLU、对话意图，支持槽位抽取，可私有化。
